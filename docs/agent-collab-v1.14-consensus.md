## 2. 四轮 challenge 完整对质链

### 2.1 第一轮：Claude 四个点（17:22 前）

1. **感知问题可能是架构自造的**：agent 被设计成彼此隔离的独立会话，L1 是在给「隔离架构」打补丁。该先问：设计的是最终形态，还是修补层？
2. **对称「同行感知」是错的抽象**：生产者（codex）需要「谁在碰我现在的文件」+碰撞提醒；质检者（claude）需要「谁改了 X、改了什么」——同一个通用 peer 段两端都不够用。
3. **人不是负担，是路由器**：第一性价值是「编排台」（人仍裁决，裁决成本从逐条转达降到一眼看清），不是「减少人的协调」。
4. **真正危险的从来不是并发，是接力**：5 分钟窗口碰撞检测答错了题——真实风险是隔 3-5 小时的接力冲突（因果链断裂）。

### 2.2 第二轮：codex 五个点（17:22）

1. **动静分离**：静态层（谁在活跃/规则）走注入，动态层（最近谁碰了 X）走 on-demand。数据支持：same_content 9,765 次命中说明能进缓存的内容恰是变化慢的。
2. **命中率不是主成本，人时才是**：deepseek-v4-flash 廉价 + proxy 自有，真贵资源是人的协调时间。
3. **先建测量系统**：但测量会被观测偏置（霍桑效应 + 口径难稳定）。
4. **感知信息必须可验证**：断言式摘要错误时是系统性误判，返回值应带证据链（commit hash/diff/时间）。
5. **真问题是会话记忆**：人开多 session 可能因长 session 记忆丢失/混淆。

### 2.3 第三轮：Claude challenge codex（17:28-17:32）

- **触发缺口反例反向适用**：codex 主动 pgrep 是用户一句话触发的，不是注入——注入「改共享文件前先查」有鸡生蛋问题（判断共享本身需要感知）。
- **26.3% 口径过宽**：50 条「要求 review」是用户主动想要的互审流程，不是负担。
- **编排台 ≠ 测量仪器**：两者约束冲突（聚合展示 vs 无偏精确），管线要分离。
- **本线程就是测试台**：用户把 claude 和 codex 分析互相转发 = L1 要替代的路由动作的微缩版。
- **codex 修正**：「状态驱动触发 = 计划里已有的 PreToolUse deny 层」→ 注入对 codex 可直接放弃，POC-1 降级为「verify deny 层够不够」。

### 2.4 第四轮：Claude challenge codex（17:35-17:37）——实证裁决

- **Challenge 1（deny 层只覆盖 claude）→ codex 实证认输**：
  - `docs/agent-collab-v1.13-plan.md:310` 明确「PreToolUse 双条件 deny | **Claude 专属**」[引用]
  - `hook/hook_codex.go` 只处理 `UserPromptSubmit / PostToolUse / Stop`，**无 PreToolUse** [实测]
  - `~/.codex/config.toml` hooks.state 注册 `post_tool_use / user_prompt_submit / stop`（+ superpowers session_start），**无写前钩子** [实测]
  - **推论**：codex 侧写前触发机制不存在，且「为 codex 新建写前信号」是伪选项（改 codex 客户端超控制面 / proxy 层无 pre-write 时机）。codex 只能弱触发（写后、下一次请求前）。
- **Challenge 2（本线程 pilot 重犯 26.3% 分类错误）→ codex 认输**：「查看 codex 的回应」是**有意对质**（要独立第二意见），不是信息同步。L1 上线后对质类转发**不该降**。正确 pilot 指标 = **信息同步类转发降不降**。
- **次要（两段式指标自相矛盾）→ 认**：放弃单一主指标，编排台上放两个正交信号（精确：git 状态碰撞；召回：无链接接力），由人裁决；proxy 自动计数只计客观的 git 状态碰撞，链接缺失作为上下文展示不参与计分。

## 5. v1.14 路线图（取代 v1.13 的注入对称 peer 段路线）

```
T3b 字段统一 + T4 rel_path 查询（合并，第一闭环）
   │  （codex apply_patch 的 *** Update File 可稳定解析；claude 绝对路径归一化）
   ▼
编排台（给人，同时是测量仪器的基础）
   │  （数据源与 T4 相同；proxy 层自动计数走独立管线）
   ▼
按角色 on-demand 查询（生产者：碰撞状态；质检者：变更史+证据链）
   │
   ▼
deny 层验证（状态驱动触发；claude 侧）→ POC-1 收尾验证
   │
   ▼
接力断链检测（因果断链，非墙钟窗口）→ 降级路径固化
```

关键依赖修正：
- **T3b 与 T4 不可拆**：数据格式证明它们是一件事的写入端和读取端（决策 58）。
- **POC-1 不再是前置阻塞**：注入对 codex 出局后，POC-1 降级为 deny 层 verify（决策 53）。
- **编排台优先于注入**：先给人看清，再谈给 agent 注入（决策 54）。
- **codex 侧写前不可行是硬约束**：T3b 不再讨论「要不要写前信号」，而是接受「codex 只能弱触发」（决策 53 + H-A12）。

## 7. Pilot 设计（以本三方线程为测试台）

**基线（[实测]）**：本线程 12 条用户消息中 6-7 条是「查看 Claude 的回应/意见」「查看 codex 的分析」——路由转达动作的微缩版。

**关键区分（决策 57）**：
- **信息同步类**（L1 应替代）：「codex 改了 X，你小心」「另一个 session 在改这个文件」——ED 里 `你需要注意 还有其他两个session也在工作` 这类。
- **有意对质类**（L1 不应替代、也不该降）：「看看 codex 说的对不对」「你有 challenge 吗」——用户要独立第二意见。

**pilot 指标**：编排台/接力检测上线后，**信息同步类转发频率下降**、对质类保持——比 ED 信号更强、更快、无业务噪音。
