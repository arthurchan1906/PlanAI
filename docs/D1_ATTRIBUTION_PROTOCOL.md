## 0. 目的与边界

- **目的**：把「MCP 工具 Agent 自发使用率」从拍脑袋变成可度量——给出可复算、可双标验证的自发率基线。
- **定位**：D1 是**抽样估计指标**，不是全量自动指标（归因需理解 prompt 与工具调用的语义关系，撞零语义地基）。形态 = 每批抽 100 条 → 双标 ≥80% → 自发率估计 + 置信区间（QA 抽样审计）。
- **非目标**：不做全量自动计数器；不替代 M 线「深度查证工具调用占比 17.2%」（那是另一个代理信号，**与 D1 分开报**）。

## 1. 判定标准（反事实 Q1/Q2）

**严禁按「user 消息是否点名工具」直接归因**（上午已证的教训：用户说目标不说工具，如「查看分析」→ agent 读讨论是任务映射）。改为**反事实问题**，标注者只需回答：

- **Q1**：工具调用是否在 user prompt 中被**明确点名**？
  - 点名 → **被动**（明确绑定）
- **Q2**（未点名时）：移除该 prompt，agent 是否**仍会**做此调用？
  - 会 → **自发**
  - 不会但属目标直接实现 → **任务映射**（不算自发）
  - 不会且**超出字面拓展** → **半自发**（有价值但非纯自发）

## 2. 标签与「半自发」严格判定（本次试点核心教训）

标签：`自发` / `半自发` / `任务映射` / `被动`。

**「半自发」必须用「超出字面」严格判定**——本次双标发现 codex 对半自发判定**偏宽**（把任务映射/被动误判为半自发），经用户裁决纠正。协议强制：

- **算半自发**（用户未点名 + agent 主动超字面检索/记录）：
  - #8「记录一下map range」→ `search_discussions` 主动回溯历史经验
  - #18「贴117KB日志+查看昨天修改」→ agent 主动 `record_bug` 定位
  - #20「提交到aipm」→ `search_context/smart_search` 主动检索「设备列表UI对齐安卓」证据
- **不算半自发**（修饰语/流程回填，反面参照）：
  - #1「站在全局视角制定方案」——「全局视角」是修饰语，`read_discussions` 读背景属任务直接实现
  - #10「查看challenge」+ 记录动作——任务完成后回填是流程一环
  - #11「已经安装了」+ 视觉工具——隐含点名验证功能，归**被动**

**规则补充（100 条正式双标新增，2026-08-28 共识）**：
- **用户点名或明确建议的检索/动作 = 任务映射**（不算法半自发）。例：#86「我建议你在 aipm 中搜索相关实现修改记录」→ 用户**明确建议搜索**，agent 14 次 `search_context` 是跟随建议，归任务映射（codex 判对，claude 原判半自发已修正）。
- **极简指令（「继续」「好的」等）**：user 未给具体目标，agent 自主 `update_task`/`record_decision`/`search_context` 推进——**最接近自发的边界，保留半自发判定**（例：#31/#42/#47）。

## 3. 标注单位：user turn

- 一个 turn = 一条 user 消息 → 下一条 user 消息之间的工具调用序列。
- 不用 session 作单位（session 里混有指令触发 + 自发调用）。
- 抽取注意：`📡` 行每调用落**2 行**（`✅结果` + 裸行），需去重；但实测 **codex 也有少量 `🛠` 行**（aipmc 6/ED 131 条，几乎全是 `list_mcp_resources` 非 aipm 工具）——D1 只统计 `📡 aipm_*` 类，`🛠` 基本排除。

## 4. 抽样策略

- **排除点破效应日**：≥ `2026-08-27`（8/27 起多轮「查看审核/分析」密集驱动调用，污染自发率）。
- **只抽 `codex-cli` + `claude-code`**：用户明确 cursor/opencode/gemini 暂不考量、甚至移除。
- **分层**：按 `项目（aipmc/ed）× agent` 均分（试点 4 组×5 条）。
- **样本量**：每批 ≥100 条（50 条 ±18% CI 太宽；试点 20 条仅验证可操作性，正式批需 100）。

## 5. 双标流程（复用 P1c 方法论）

- **观察者隔离（硬约束）**：codex 先独立标注（不读 claude），claude 再独立复标（不读 codex）——两边互不看见，最后对比。实现者不得标注自己的结果。
- **一致率**：严格按 label 相同计，≥80% 达标。
- **分歧**：记录到标注集文件 → 人工裁决 → 作为参照范例。
- **输出**：标注集文件（样本+两标+裁决记录）→ 自发率估计 + CI。
- **标注集兼作未来自动规则的校准集**（若将来想上规则，用它验证）。
- **参照范例前置**：本批 100 条裁决（`docs/D1_DISAGREEMENTS_100_ADJUDICATION.md`）须在下一批复测开工前并入协议/参照集，否则复测会用到未强化的协议。
- **join 键**：标注/裁决/gold 跨文件一律用 `(project, agent, turn)` 匹配，勿用 `idx`（两套 `idx` 语义见头部注释）。

## 7. 对 P0「5%→30%」的影响

- 原目标参考「5% 自发率」（7/28 决策）——**新基线显示 0%（纯）与 15%（含半自发）**，原 5% 可能是历史统计误差（未经双标验证）。
- 两条可观测增长轨迹：
  - **纯自发线**：0% → 30%（激进，接近每个任务都有自发）

- P0 验收应**分列报两条线**，禁止单数字断言「达到 30%」。

### 7.1 自发率低的失效根因（四层模型，2026-08-28 ED 实证）

> 来源：aipmc+ED 双会话独立验证（ED-claude 实测经历 compaction、ED-codex 补设计结论、aipmc codex 自我观察）。修正此前的「单一提示时机」假设。

D1 自发率≈0 的根因**不是**「agent 不愿用」或「工具没被唤起」单一机制，而是**四层**：

| 层 | 失效机制 | 实证 | P0 应对 |
|---|---|---|---|
| ① **动作点未固定** | 该用的工具不在 agent 的确定性动作清单里（开工/get_briefing、确认 bug/record_bug、决策前/list_decisions、commit 前） | ED-claude T1：3 例漏用全是「不在思维候选集」，无「犹豫时刻」 | **确定性代码钩子**（开工/根因确认/决策/commit 时 hook，非 prompt 提示） |
| ② **规范语义模糊** | CLAUDE.md 指令映射错误（「decision 先查」→ 执行成 search_context）、工具职责归属不清（record_bug 到底谁该记） | ED-claude B：record_bug 职责归属不清 | **规范措辞对齐**（让指令直接映射到工具，而非语义相近的其它工具） |
| ③ **compaction 后注入过期** | 系统级上下文压缩后，SessionStart 注入成早间快照，后半程 PM 变化不可见 | ED-claude C：compaction 后完整忘记 record_bug，但 43 工具全在手 | **注入随 PM 变更刷新** / compaction 时重注入 |
| ④ **工具输出形状不匹配** | get_briefing 输出的是 PM 事件流/管理视图，而 agent 实际需要「代码上下文卡」（相关文件 × bug × decision × 验证台账）——改的是「输出」而非「唤起」，故独立于②规范语义模糊 | ED-claude B：get_briefing 是输出形状问题，agent 拿到的事件流不是它要找的代码上下文 | **改工具输出形状**：get_briefing → agent_briefing；新增代码上下文卡（相关文件 × bug × decision × 验证台账） |

**关键设计结论（ED-codex 贡献）**：
- **「prompt 注入会被压缩吃掉，代码钩子不会」**——真正关键的唤起（record_bug/验证台账/开工上下文卡）不能只靠注入，要靠**确定性代码钩子**。
- **「工具清单就绪 ≠ 意图就绪」**——没人帮 agent 想起，就不会想起。
- **P0 机制应按四层各做一条**：动作点确定性代码钩子 / 规范措辞对齐 / 注入随 PM 变更刷新 / 改工具输出形状（agent_briefing + 代码上下文卡）。

**数据口径提醒（M1a 对账）**：自我报告的调用数会漏（agent 记忆不全），应**以日志为权威**（`[MCP]` 全量）。本协议的自发率统计一律基于 `discussion_log`/`[MCP]` 日志，不以 agent 自述为准。
