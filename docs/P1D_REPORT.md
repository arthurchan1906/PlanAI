## 1. P3 时间/存在性类基线定义

三个检测点均为**时间窗口/存在性判定**：L1 负责候选定位（时间窗口、事件对），L2 语义层负责「引用/采纳/该沉淀」判定（SPEC §2.1 分层：时间/存在性判定归 P1 层）。以下定义使每个检测点**可计算、可复核、绑定 P3 改进**。

### 1.1 知识同步延迟（Knowledge Sync Delay）

| 项 | 定义 |
|---|---|
| 检测对象 | 跨 agent 关键结论（明确指令/裁决/纠偏）从**产出**到**被采纳**的延迟 |
| 产出锚点 | 结论消息在 discussion_log 落库时刻（`role=assistant` + 含裁决/指令语义，L2 判定） |
| 被采纳操作化 | 读到（后续消息**引用/提及**该结论，L2 语义判定，L1 词面匹配不可靠——SPEC 第五轮补）后 **N=5 条消息内**出现行为改变（修复/检索/建 task/改方案）= 采纳 |
| 读到未采纳 | 读到但 N 条内行为未变 = **「读到未采纳」事件**（codex 13:43 现场），不记「延迟无限」 |
| 数据源 | discussion_log（跨 agent 消息）+ tasks/commits/decisions（行为改变落地物） |
| 计算口径 | 延迟 = 采纳行为时刻 − 结论产出时刻；按工作消息计数（跨夜休眠扣除，T1 同源口径）；仅统计「被读到」的结论（未被读到的结论不产生延迟事件，记 `unread`） |
| 阈值锚点 | P3 改进「未读点评推送」目标：上线后延迟 <2 分钟（SPEC §2.1） |

**基线实测（方向性，2026-08-27 现场样本）**
- ✅ **采纳延迟 1.5 分钟**：Claude 8/27 13:11:26 挑战「T3b 现在是什么状态？有没有 task？谁做？」→ codex 13:12:57 创建 T3b task（`task-20260827-131257-750e10`，标题即挑战要求的「claude tool 空 metadata 修复 + P1a 覆盖缺口回测」）。产出→采纳 = 1 条消息内（采纳即刻，无「读到未采纳」）。
- ⚠️ 无推送时基线：8/27 上午 codex 03:58-09:03 的全局分析→Claude 09:06 读到并核实——采纳发生在「下次主动读取」时（无实时推送，延迟 = 读取周期，本会话为分钟级）。
- 负向锚点（SPEC 既有）：9fc1ffb 读 selector 指令→修复（采纳）；codex 13:43 读到流程要求却直接提交（**读到未采纳**事件）。

### 1.2 知识沉淀时机（Knowledge Sink Timing）

| 项 | 定义 |
|---|---|
| 检测对象 | 「该沉淀的结论」（裁决/机制级认知，L2 判定该沉淀）从结论产生到**当天**沉淀为 decision/记录 |
| 沉淀落地物 | decisions 表（status=accepted/proposed）或 session 备注/thread（L2 判定记录形态） |
| 数据源 | discussion_log（结论首现）+ decisions（date 字段）/threads（created_at） |
| 计算口径 | 结论首现时刻（discussion_log 首条含该结论消息）→ 沉淀物 date/created_at；**跨天 = 未及时沉淀**；不跨天 = 当日沉淀 ✓ |
| 阈值锚点 | P3 改进「决策前置提醒」目标：结论产生当天落地（SPEC 8/19 晚结论当天落地为正向锚点） |

**基线实测（方向性，8/27 三条决策全当天沉淀）**
- D 线：结论讨论 08:58 起点 → `decision-20260827-144909-c3d06b` 14:49 沉淀，同日 ✓（延迟 5.9h）
- B 线约束：8/26 讨论「反馈只注入行为事实」→ `decision-20260826-172138-fb48b1` 8/26 当天沉淀 ✓
- 机制 4 砍掉：8/27 10:09-10:10 讨论 → `decision-20260827-120457-f9ff39` 12:04 沉淀，同日 ✓（延迟 ~2h）
- 负向锚点（SPEC 既有）：8/19 晚「API 死刑 ≠ 机制死刑」结论当天未沉淀为 decision（8/19 决策记录缺失，为「该沉淀未当天沉淀」基线样本）

### 1.3 复盘存在性（Retrospective Existence）

| 项 | 定义 |
|---|---|
| 检测对象 | saga（有明确开始/结束边界的长周期工作，如 P0a1a→P0b 门禁链、双 agent 大版本方案）结束后是否自动生成时间线/复盘 |
| 复盘落地物 | threads 表（source=auto 为自动复盘；source=manual 为人工复盘）或 docs/*REPORT 报告 |
| saga 边界 | 起：首条 saga 相关 user prompt/task 创建；止：验收报告/门禁通过时刻（复用事件边界表口径） |
| 数据源 | threads + docs/ 报告 + tasks（状态流） |
| 计算口径 | saga 结束（验收时刻）→ 复盘物创建；**存在性判定**：有复盘 = ✓（记录延迟），无复盘 = ✗（缺失事件） |
| 阈值锚点 | P3 改进「复盘助手」目标：saga 结束后自动生成（当前基线：人工复盘，延迟 0.5-1 天） |

**基线实测（方向性）**
- ✅ 复盘存在：P0a1a→P0b saga（8/22-8/24）→ `thread-20260825-132004-9a9519`「EVAL 管线 P0a1a→P0b 门禁通过」8/25 13:20 创建，saga 结束（8/24 报告）后 ~1 天复盘 ✓（**人工**复盘，非自动）
- ✅ 复盘存在：8/26-8/27 测量-理解-注入闭环整合讨论 → `thread-20260826-170920-94b5ef` 8/26 当天创建 ✓
- ⚠️ 未结束 saga 不判缺失：8/27 五线工作（B/D/C/M/T3b）M 线产出物 3 排 9/3 后，saga 未结束，复盘缺失不判定（防误报）
- 负向锚点（SPEC 既有）：8/19 分享扩展 saga 结束后无时间线/复盘记录（复盘缺失基线样本，对应复盘助手改进动机）
