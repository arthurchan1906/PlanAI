# 02 · 类型系统与接口

> 本章是 Go 心智模型的核心：没有类继承，struct + interface 组合出一切。
> 来源：原 `GO_GUIDE.md` 概念篇 §4-5 + 语法篇 §4/§6 + 实战篇 §1/§4 + 高频语法。

---

## 1. 没有类，没有继承

Go 没有 `class` 关键字。用 **struct + 方法** 代替：

```python
# Python
class Task:
    def __init__(self, title):
        self.title = title
    def display(self):
        return self.title

# Go
type Task struct { Title string }
func (t Task) Display() string { return t.Title }
```

没有继承，用**组合**（embedding）：

```go
type BugReport struct {
    Task         // 嵌入 Task, BugReport 自动获得 Task 的所有字段和方法
    Severity string
}
b := BugReport{Task: Task{Title: "崩溃"}, Severity: "critical"}
fmt.Println(b.Title)    // 直接访问嵌入 struct 的字段
```

## 2. Interface：隐式满足（最重要的概念）

Go 的 interface 不需要显式声明"我实现了这个接口"——只要有对应的方法就行：

```go
// 定义接口
type Embedder interface {
    Embed(texts []string) ([][]float64, error)
}

// 任何有 Embed 方法的类型自动实现 Embedder — 不需要 implements 关键字
type HTTPClient struct { ... }
func (c *HTTPClient) Embed(texts []string) ([][]float64, error) { ... }

// 使用 — HTTPClient 自动满足 Embedder
var e Embedder = &HTTPClient{endpoint: "http://..."}
```

**Python 对比**：Python 的 Protocol / ABC 需要显式继承或 `@runtime_checkable`。Go 的 interface 是**编译时检查的鸭子类型**——只要方法签名匹配就行，不需要标记。

**C++ 对比**：相当于抽象基类，但**不需要 `: public Interface`**。没有 vtable 的手工维护——Go 编译器自动判断一个类型是否满足接口。这比 C++ 的 `virtual` + `override` 更轻，代价是少了一点"显式声明"的可读性。

> 当前项目 `ai/interface.go` 定义了 **3 个接口**：`Embedder`、`Summarizer`、`Searcher`（`Searcher.RankSimilarity(query, candidates) ([]RankedResult, error)` 用于语义相似度排序）。`ai/noop.go` 提供 3 个对应空实现——AI 未配置时优雅降级。

## 3. 基础类型

```go
// struct = C struct / Python dataclass
type Task struct {
    ID     string `json:"id"`       // 结构体标签 (类似 Python __annotations__)
    Title  string `json:"title"`
    Status string
}

// 创建实例——Python: Task(id="1", title="test")
t := Task{ID: "1", Title: "test"}

// 指针——Go 特有。&取地址, *解引用。类似 C 指针但无算术。
p := &t          // p 是指向 t 的指针
p.Title = "new"  // 自动解引用, 不用写 (*p).Title

// interface = Python 的 Protocol/ABC, JS 的 duck typing
type Embedder interface {
    Embed(texts []string) ([][]float64, error)
}
// 任何有 Embed 方法的类型自动实现 Embedder（隐式, 不需要 implements 关键字）

// map = Python dict / JS object
m := map[string]interface{}{"key": "value"}   // map[键类型]值类型{初始化}
v := m["key"]   // 取值, 不存在返回零值

// slice = Python list / JS array
ids := []string{"a", "b", "c"}   // 类型固定
ids = append(ids, "d")           // 追加元素（返回新 slice）
```

## 4. 指针 — 对 C/C++ 读者最重要

Go 的指针和 C 一样（存地址），但更安全——没有指针算术：

```go
x := 42
p := &x      // C: int *p = &x;    Python: 不能直接操作指针
*p = 100     // C: *p = 100;       修改 x 为 100

// struct 方法用指针接收者——避免复制整个 struct
func (t *Task) SetStatus(s string) {
    t.Status = s   // 修改原始 Task
}
// 等价 Python:
// def set_status(self, s):
//     self.status = s
```

**对 C/C++ 读者，几个关键差异**：
- **没有指针算术**：`p++`、`p[5]` 这种 C 写法在 Go 里直接编译报错。指针只能 `&` 取地址、`*` 解引用、以及字段访问 `p.Field`（自动解引用）。
- **`nil` 而不是 `NULL`/`nullptr`**：`if p == nil` 等价于 C 的 `if (p == NULL)`。
- **GC 替你管理内存**：不需要 `free()` / `delete`，也不会有 C++ 的悬垂指针/use-after-free。代价是不能自己控制析构时机（用 `defer` + 显式 Close 代替 RAII）。
- **`&` 一个局部变量是安全的**：Go 的逃逸分析会自动把它移到堆上。C 里返回局部变量地址是未定义行为，Go 里完全合法。

### 值接收者 vs 指针接收者

```go
// 值接收者 — 操作的是副本
func (t Task) SetTitleBad(s string) { t.Title = s }     // 无效！外面不变

// 指针接收者 — 操作的是原件
func (t *Task) SetTitleGood(s string) { t.Title = s }   // 正确

// interface 满足规则不同:
type Updater interface { Update() }
func (t Task) Update()  {}   // Task 满足 Updater, *Task 也满足
func (t *Task) Update() {}   // 只有 *Task 满足 Updater, Task 不满足！

// 规则: 指针类型的方法集包含值接收者的方法，反过来不行
```

**对 C++ 读者**：这等价于"成员函数参数按值还是按引用"。`func (t Task)` = 按值传 `this`（拷贝一份，改的是副本）；`func (t *Task)` = 按引用传 `this`（改原件）。Go 只是把 `this` 显式写在了方法名前面。**大 struct 一律用指针接收者**——和 C++ 里 `const` 大对象传引用一个道理，避免复制开销。

## 5. 空接口 any + 类型断言

```go
// 空接口 interface{} / any = Python 的 object / typing.Any
var data interface{} = "hello"
s, ok := data.(string)  // 类型断言（Python: isinstance(data, str)）
```

### map[string]any 类型断言 — 项目里到处都是

```go
// 从 JSON 解析出来的 map 里取值，必须做类型断言
cfg := map[string]any{}
hooks, ok := cfg["hooks"].(map[string]any)   // 断言 cfg["hooks"] 是 map[string]any
if !ok {
    hooks = map[string]any{}                  // 断言失败，给默认值
}

// 嵌套断言
if tools, ok := hooks["PostToolUse"].([]any); ok {
    for _, t := range tools {
        if m, ok := t.(map[string]any); ok {
            cmd := m["command"].(string)      // 单返回值断言，如果不是 string 会 panic
        }
    }
}

// str() 辅助函数 — AIPMC 项目自定义，安全取字符串
func str(v any) string {
    if s, ok := v.(string); ok { return s }
    return ""
}
```

**为什么这么麻烦？** 因为 Go 的 `json.Unmarshal` 到 `map[string]any` 时，所有值都是 `any`。静态类型语言必须手动断言。项目里 `u.Str()` 和 `api/util.go` 的 `pstr()` 就是为这个写的（安全取字符串，取不到返回默认值）。

### json 标签的常见选项

```go
type ToolInput struct {
    Command   string `json:"command"`             // 字段名映射
    FilePath  string `json:"file_path"`           // Go 用驼峰, JSON 用下划线
    Content   string `json:"content,omitempty"`   // 空值时从 JSON 中省略
    OldString string `json:"old_string,omitempty"`
    Ignored   string `json:"-"`                   // 完全不序列化
}
```

### 匿名 struct — JSON 解析的利器

```go
// 定义 struct + 初始化 + JSON 反序列化 一次搞定
var raw struct {
    ToolName  string `json:"tool_name"`
    ToolInput struct {
        FilePath  string `json:"file_path"`
        OldString string `json:"old_string"`
    } `json:"tool_input"`
}
json.Unmarshal(data, &raw)

// Python 等价: raw = json.loads(data); raw["tool_input"]["file_path"]
```

## 6. 泛型 — 项目里很少用（仅 2 处）

Go 1.18+ 才有泛型，AIPMC（go 1.25）只在两处用：

```go
// api/config.go:50 — 把 map 通过 JSON 转成任意类型的 struct
func mapProfile[T any](m map[string]any) T {
    data, _ := json.Marshal(m)
    var p T
    json.Unmarshal(data, &p)
    return p
}

// proxy/proxy.go:1178 — 安全的切片截断
func firstN[T any](slice []T, n int) []T {
    if len(slice) <= n {
        return slice
    }
    return slice[:n]
}
```

> **对 C++ 读者**：`[T any]` 就是 C++ 的 `template <typename T>`，但 Go 的泛型设计得更克制——只支持接口约束，没有偏特化、没有模板元编程。读项目时**看到 `[T any]` 知道是泛型函数即可**，99% 的代码不涉及。

## 7. 为什么这么设计：类型系统的原理由来

### 7.1 为什么 Go 没有继承？

不是"忘了加"，而是**刻意砍掉**。Go 设计团队对 C++/Java 继承体系的观察：

1. **继承树很脆弱**：改基类的一个方法，所有派生类行为都变，牵一发动全身。
2. **继承隐藏了代码路径**：`obj.method()` 到底调到哪个实现，要看整个继承链——C++ 有虚表、Java 有方法解析，认知负担重。
3. **组合更简单**：`A 有一个 B` 比 `A 继承 B` 更容易推理。Go 用 struct embedding 提供"组合 + 字段提升"的语法糖，但没有多态继承。

**结果**：Go 的"多态"完全交给 interface。你想让一个函数接受"任何能 Summarize 的东西"，写 `func f(x Summarizer)`，编译器检查。没有继承树，只有契约。

### 7.2 为什么 interface 是隐式满足？

C++ 的 `: public AbstractClass` 和 Java 的 `implements Interface` 都是**显式声明**。Go 把它去掉，理由是：

- **解耦**：定义接口的一方不用知道谁实现了它，实现的一方不用知道自己"属于哪个接口"。`ai/interface.go` 定义 `Summarizer`，`ai/http_client.go` 的 `Client` 根本不用 import 接口文件——它们靠**方法签名**对上。
- **更小的抽象**：Go 谚语 *"The bigger the interface, the weaker the abstraction"*。隐式满足鼓励你定义小接口。标准库 `io.Reader` 就一个方法：
  ```go
  type Reader interface { Read(p []byte) (n int, err error) }
  ```
  任何有 `Read` 方法的东西都是 `io.Reader`——文件、网络连接、bytes.Buffer、gzip 包装……这就是 Go 生态里几十个库能无缝组合的原因。

**代价**：IDE 不能像 C++/Java 那样"列出实现了此接口的所有类"——不过 `go doc` + grep 方法签名可以弥补。

### 7.3 为什么泛型到 Go 1.18（2022）才有？

泛型是最反复讨论的提案（有 5+ 版设计稿，2010 年就有人提）。原因：

1. **设计者担心复杂度失控**：看 C++ 模板元编程、Java 泛型的通配符地狱，他们宁可没有。
2. **Go 的哲学是"够用"**：绝大多数代码不需要泛型。`[]T`、`map[K]V` 是内建泛型，用户代码通常可以靠 `interface{}` + 类型断言硬扛（丑但能用）。
3. **拖到 1.18 是因为社区压力**：基础设施库（集合、管道）确实需要。

**结果**：Go 的泛型只支持**接口约束**（`[T any]` 是 `[T interface{}]` 的缩写），没有偏特化、没有模板递归、没有运算符重载。AIPMC 全项目只有 2 处——这就是"够用就行"的实证。

## 8. Go 的思考方式：接口与类型的几条心法

### 8.1 "Accept interfaces, return structs"

Go 社区最著名的接口心法：**函数参数用接口（宽进），返回值用具体 struct（窄出）**。

```go
// ✅ 好：接收接口
func GenerateL2Summary(messages []map[string]any, summarizer ai.Summarizer) string

// ❌ 不好：接收具体类型，调用方被绑死
func GenerateL2Summary(messages []map[string]any, client *ai.Client) string
```

**为什么**：接收接口 = 调用方可以塞任何实现（mock、noop、真实 client）；返回具体 struct = 调用方拿到确定字段，不用猜接口背后是什么。项目里 `session.Run` 接收 `ai.Summarizer`（接口）正是这个套路。

### 8.2 小接口 > 大接口

Go 谚语 *"The bigger the interface, the weaker the abstraction"*。一个接口超过 3 个方法，就该怀疑它是不是太"胖"了。项目 `ai/interface.go` 的 3 个接口每个都只有 1 个方法：

```go
type Embedder  interface { Embed(texts []string) ([][]float64, error) }
type Summarizer interface { Summarize(text, instruction string) (string, error) }
type Searcher  interface { RankSimilarity(query string, candidates []string) ([]RankedResult, error) }
```

**思维方式**：接口不是"这个类的完整能力清单"，而是"调用方需要的最小契约"。每个调用方各定义自己需要的那个小接口，而不是共享一个上帝接口。

### 8.3 指针 vs 值：先想"要不要共享"

选择值接收者还是指针接收者，先问一个问题：**这个方法要修改接收者吗？** 要 → 指针；不要 → 值（小 struct）或指针（大 struct 防复制）。

- 值接收者：操作副本，适合 getter（`func (t Task) Display() string`）
- 指针接收者：操作原件，适合 setter（`func (t *Task) SetStatus(s string)`）
- **方法集规则**：`*T` 的方法集包含 `T` 的；`T` 的不包含 `*T` 的。所以接口 `Updater` 若用指针实现，只有 `*Task` 满足，`Task` 不满足。

> **对 C++ 读者**：这和你决定成员函数是否 `const`、参数是否传引用是同一个思考。只是 Go 把选择权放到了每个方法签名上，且编译器在"该用指针时用了值"会立刻报错（调用处无法修改）。

### 8.4 空接口是"约定"不是"兜底"

`interface{}` / `any` 是"我不知道是什么"。项目里用它是因为 JSON 动态结构，但**有经验的 Go 作者会尽快把它转成具体类型**：

```go
func pstr(m map[string]any, key, def string) string {
    if v, ok := m[key]; ok {
        if s, ok := v.(string); ok {   // 尽快断言成 string
            return s
        }
    }
    return def
}
```

**思维方式**：`any` 只是中转站，不是终点。拿到 `any` 立刻类型断言到具体类型，让后续代码类型安全。
