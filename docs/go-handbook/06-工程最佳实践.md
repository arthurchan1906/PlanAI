## 1. 包管理 — module 和 import path

### go.mod 文件（当前真实值）

```
module aipmc          ← 模块名——所有内部 import 都以此开头

go 1.25               ← Go 版本

require (
    modernc.org/sqlite v1.29.5   // 纯 Go 实现的 SQLite，不需要 CGO
    // ...
)
```

### 项目内引用

```go
import "aipmc/ai"      // 指向项目根目录下的 ai/ 子目录
import "aipmc/store"   // 指向 store/ 子目录
```

`aipmc` 是 module 名，`ai` 是相对于 module root 的目录路径。两者拼接就是 Go 编译器查找代码的路径。

**和 Python 的区别**：Python 的 import 基于文件系统路径（`from .ai import client`）。Go 的 import 基于 module 命名空间——完全无视文件存放位置，只看 `go.mod` 里写的 module 名。

### 可见性规则

```go
func PublicFunction() {}   // 大写开头 = 导出（其他包可用）
func privateFunction() {}  // 小写开头 = 包内私有

type ExportedType struct {}  // 大写 = 导出
var privateVar string         // 小写 = 私有
```

没有 `public` / `private` 关键字——靠首字母大小写区分。这是 Go 最简洁的设计之一：一眼看出可见性。

> **对 Python/C++ 读者**：这就是 Python 的 `_underscore` 约定 / C++ 的 `public/private`，但 Go 把它做成了**编译器强制**——小写函数被别的包引用，编译直接报错。

## 2. Interface 驱动设计 — 真实项目范式 `ai/`

这是 Go 最重要也最常用的设计模式：定义接口 → 写真实实现 → 写空实现（用于降级/测试）。

### 接口定义 (`ai/interface.go`)

```go
type Summarizer interface {
    Summarize(text, instruction string) (string, error)
}
```

只有 4 行。不需要声明"谁实现了它"——Go 编译器自动检测。

### 真实实现 (`ai/http_client.go`)

```go
type Client struct {
    endpoint string
    model    string
    apiKey   string
}

// Client 自动实现 Summarizer — 因为有 Summarize 方法
func (c *Client) Summarize(text, instruction string) (string, error) {
    // ... HTTP 调用真实 LLM ...
}
```

注意：`Client` 的 struct 定义里**没有任何 `implements Summarizer` 标记**。Go 的 interface 满足是隐式的——编译器看到 `Client` 有 `Summarize(text, instruction string) (string, error)` 方法，就自动认为它实现了 `Summarizer`。

### 空实现 / 降级 (`ai/noop.go`)

```go
type noopSummarizer struct{}

func (noopSummarizer) Summarize(text, instruction string) (string, error) {
    return text, nil  // 不报错，原样返回输入文本
}
```

注意：`noopEmbedder` 返回错误 `errNoConfig`（让调用方能检测到 AI 未配置），而 `noopSummarizer` 原样返回文本——**每个 noop 的降级行为都刻意设计成"最不破坏流程"的样子**。这就是接口驱动的精髓：上层代码不需要关心用的是真实实现还是 noop，行为是等价的（只是质量不同）。

### 消费方代码怎么用 (`dispatch.go`)

```go
var summarizer ai.Summarizer           // 声明为接口类型
if application.AI() != nil && application.AI().Enabled() {
    summarizer = application.AI()      // 有 AI → 用真实实现
}                                      // 否则 summarizer = nil
result, _ := session.Run(session.RunOpts{
    Summarizer: summarizer,            // 可以是 nil！
})
```

**关键**：`session.Run` 接收 `ai.Summarizer` 类型，但允许 nil 传入——内部有 nil check，AI 不可用时自动降级：

```go
// session/summary.go
func GenerateL2Summary(projectPath string, messages []map[string]any, review ReviewResult, summarizer ai.Summarizer) string {
    if summarizer == nil {
        return ""   // 优雅降级
    }
    // ...
}
```

**为什么这样设计**：不用到处写 `if config.AIEnabled { ... }`。调用方只需决定"有没有 summarizer"，实现方自己处理 nil。这比 Python 的 optional + None check 更清晰——接口本身就是 nil-able 的。

### 对比：Python 怎么做这件事

```python
# Python 的 Protocol（需要显式标记或 runtime check）
from typing import Protocol

class Summarizer(Protocol):
    def summarize(self, text: str, instruction: str) -> str: ...

# 或者更常见：直接传 Optional[Callable]
def generate_l2_summary(messages, summarizer=None):
    if summarizer is None:
        return ""   # 同样的 nil check
```

Go 版本有两个优势：
- 接口在编译时检查——拼错方法名或参数类型，编译器立即报错
- 不需要 `Optional[Callable]` 这种复杂类型标注——`ai.Summarizer` 就是 nil-able

## 3. 依赖注入 — 函数当参数传

`session.RunAuto` 的第一个参数是一个函数（`session/auto.go:20`）：

```go
func RunAuto(getSummarizer func(projectPath string) ai.Summarizer, interval time.Duration, projectPaths []string)
```

调用方（`main.go:731`）传入闭包：

```go
session.RunAuto(func(p string) ai.Summarizer {
    return application.SummarizerFor(p)
}, 30*time.Minute, otherProjects)
```

**为什么这么设计**：L2 摘要要用**每个项目自己的** AI 模型。如果传固定值，配置改了必须重启；传**函数**（惰性求值），每次 tick 现算——配置热更新无需重启。这是 Go 里做依赖注入的轻量方式，不需要任何 DI 框架。

## 4. Struct Embedding — 组合代替继承

Go 没有类继承。用 struct embedding 复用字段和方法。两个真实例子：

### 例子 A — 匿名 struct 缓存 (`proxy/context_inject.go`)

```go
var sessionCache struct {      // ← 匿名 struct
    mu        sync.RWMutex     // ← embedding: sessionCache 自动获得 Lock/Unlock/Rlock/RUnlock
    goals     []string
    updatedAt time.Time
    ttl       time.Duration
}
```

`sessionCache.mu.Lock()` — 通过字段名访问（也可以省略 `.mu` 直接用 `sessionCache.Lock()`，但不推荐——会掩盖调用意图）。

### 例子 B — 接口包装器 (`proxy/proxy.go:303`)

```go
type responseWrapper struct {
    http.ResponseWriter    // 嵌入接口 — 提升所有方法
    status int
    size   int
}
func (rw *responseWrapper) WriteHeader(code int) {
    rw.status = code
    rw.ResponseWriter.WriteHeader(code)
}
```

**对 C++ 读者**：struct embedding 长得像继承，但语义是**组合**。`responseWrapper` 嵌入 `http.ResponseWriter` 并重写 `WriteHeader`——读起来像 C++ 派生类 override 虚函数，但 Go 里是"内嵌接口，提升所有方法，再覆盖感兴趣的"。没有虚表，没有 `virtual` 关键字，多态走 interface。如果你习惯 C++ 的"基类指针调派生方法"，Go 里是"interface 变量持任意满足者"。

### 例子 C — 序列化时附加字段 (`session/review.go:450`)

```go
type payload struct {
    ReviewResult                    // 所有 ReviewResult 字段被提升
    QualityScore int `json:"quality_score"`
}
p := payload{ReviewResult: r, QualityScore: r.QualityScoreValue()}
```

匿名 struct 嵌入 `ReviewResult`，把它的字段全部"提升"出来，再补一个 `QualityScore int`——不改原 struct 就能在 JSON 里附加字段。

## 5. 组织大型代码库 — eval 包的统一形状

AIPMC 的 `eval` 包有 20 多个"探测器"（`pq_*.go`），每个都长一个样：

```go
// 1. Params 结构体 + 默认值构造器（可调阈值）
type DeadloopParams struct { ... }
func DefaultDeadloopParams() DeadloopParams { ... }

// 2. 检测函数 — 输入 turns，输出候选
func FindDeadloops(turns []Turn, p DeadloopParams) []DeadloopCandidate { ... }

// 3. 人类可读渲染器
func FormatDeadloopHuman(cands []DeadloopCandidate) string { ... }
```

`eval/pq_process.go:28 BuildProcessReport` 是它们的编排者。

**对 C++/Python 读者**：这是 Go 组织大型代码库的方式——**不用继承、不用注册表、不用类层次**，靠**文件名约定 + 一致的函数签名**。新加一个探测器 = 新建一个 `pq_xxx.go` 文件，按三个函数模板写。团队协作时，读任何新文件都像读老朋友。

## 6. 后台长任务必须自己 recover

任何 `go func(){...}()` 后台任务，只要它可能 panic，就必须在内部 `defer recover()`。见 [04 · 错误处理](04-错误处理与资源管理.md) §6。

## 7. 学习纪律

1. **永远 `go build ./...` + `go vet ./...`**，编译通过 = 类型对；vet 通过 = 常见错误被揪出来。这两关过了再谈逻辑。
2. **读代码时先找函数签名**（`func Name(...)` ），再找它调的包——Go 的依赖方向一目了然（import 列表就是依赖图）。
3. **改代码最小化**：每个文件顶部 `package xxx` 决定可见性，小写函数=私有。你不小心改了小写函数名，编译器会立刻告诉你"哪里还引用了它"。
4. 想查某个标准库怎么用，`go doc fmt.Println` 一行命令即可——不用上网。

## 8. 为什么这么设计：工程哲学的原理由来

### 8.1 gofmt — 为什么格式化是强制的？

Go 从 1.0 起自带 `gofmt`，编译器的 `go build` 之前所有 Go 代码必须按它格式化（`go fmt` 就是 `gofmt -w`）。设计者 Rob Pike 说过一句名言：

> **"gofmt 的风格谁都不喜欢，但 gofmt 是所有人的最爱。"**
> *gofmt's style is nobody's favorite, yet gofmt is everyone's favorite.*

意思是：格式化标准本身无所谓好恶，**关键是统一**。没有它，团队会花无数时间争论"缩进 2 格还是 4 格""花括号换行不换行"。Go 直接消灭这个争论——写出来的代码全都一样，代码评审只看逻辑不看风格。

**思维方式**：工具化代替约定。凡是"可以用工具强制的事"，就别靠人自觉。

### 8.2 为什么包是设计的基本单位？

Go 的可见性规则（大写=导出、小写=私有）是**包级别**的，不是类级别的。这意味着：

1. **包是封装的最小单元**：`db` 包内部的辅助函数（`initSharedLogger` 之类）别的包碰不到。
2. **包是复用的最小单元**：import 一个包，就是拿到它的导出 API。包名就是命名空间，也决定文档结构（`go doc aipmc/store` 列出整个包）。
3. **依赖方向由 import 决定**：包 A import 包 B，A 就依赖 B。读代码时看 import 列表就能画依赖图——Go 没有循环 import（编译器禁止），所以依赖关系永远是有向无环图。

**思维方式**：设计一个新功能，先想"它属于哪个包"，而不是"它属于哪个类"。包边界 = 职责边界。

### 8.3 Go 的命名哲学：短名字 + 一致性

- 变量名尽量短：`i`、`s`、`n`、`db`。Go 社区认为**短名字在局部作用域是清晰的**（作用域越小，名字可以越短）。
- 但是：**包外的导出符号要描述性**——`CreateTask` 而不是 `CT`。
- 方法接收者统一用 1-2 个字母：`(t *Task)`、`(s *Server)`、`(c *Client)`。项目里全部遵守。

**思维方式**：命名规则是"作用域越大越详细"。局部 `for i` 可以，全局 `func CreateTask` 必须完整。

### 8.4 module 的历史 — GOPATH → Go Modules

早期 Go 没有依赖版本管理，所有项目塞进 `$GOPATH/src`。2018 年 Go 1.11 引入 **Go Modules**，2021 年（Go 1.16）成为默认。

```
go.mod  = 项目的依赖清单 + 模块名 + Go 版本
go.sum  = 依赖哈希锁（保证可复现构建）
go get  = 添加/更新依赖
```

**项目当前 `go.mod`**（2026-08）只有 4 个直接依赖，其余是传递依赖：

```
module aipmc

go 1.25

require (
    github.com/google/uuid v1.3.0
    golang.org/x/term v0.44.0
    golang.org/x/text v0.38.0
    modernc.org/sqlite v1.29.5   // 纯 Go 的 SQLite，无 CGO
)
```

### 8.5 十条 Go 谚语（Rob Pike, Gopherfest 2015）

| 谚语 | 含义 |
|---|---|
| **Make the zero value useful** | 零值要可用（见 01 章 §9.3） |
| **The bigger the interface, the weaker the abstraction** | 小接口 > 大接口（见 02 章 §8.2） |
| **A little copying is better than a little dependency** | 少量复制好过引入依赖 |
| **Clear is better than clever** | 清晰 > 炫技 |
| **Errors are values** | 错误是数据流（见 04 章 §8.5） |
| **Don't communicate by sharing memory** | 用 channel 通信（见 03 章 §6.2） |
| **Interface satisfaction is implicit** | 接口隐式满足 |
| **The package is the unit of design** | 包是设计单位 |
| **Concurrency is not parallelism** | 并发 ≠ 并行 |
| **Documentation is for users** | 文档写给使用者 |

这些谚语就是 Go 社区的"设计价值观"。读到陌生代码时，用它们判断"这样写 Go 吗"。
