## 1. 并发模型：goroutine vs 线程 vs async

```go
// Go — 启动一个 goroutine (轻量级线程, ~2KB 栈)
go computeEmbedding(id, content)

// Python — 线程或 asyncio
// threading.Thread(target=compute, args=(id, content)).start()
// asyncio.create_task(compute(id, content))

// JS — 异步 Promise
// Promise.resolve().then(() => compute(id, content))
```

**关键区别**：
- Python 的 `threading` 受 GIL 限制，CPU 密集任务不能真并行
- JS 的 `async/await` 是协程，没有真正的多线程
- Go 的 goroutine 是**真正的轻量线程**，可以跑成千上万个，Go runtime 自动调度到 OS 线程上

**但注意**：goroutine 不会阻止进程退出。主函数 `return` 时所有 goroutine 全部杀。Web 服务是长时运行所以没问题；CLI 短命令中 goroutine 会丢失。

**对 C/C++ 读者**：goroutine 就是 `pthread_create`，但你去掉了 `pthread_join`、`pthread_mutex` 的手工配管——Go runtime 自动调度。开一万个 goroutine 跟开一万个线程不是一回事：goroutine 初始栈才 2KB（线程默认几 MB），创建销毁几乎零成本。C++ 里你担心的"线程池、任务队列、栈大小、竞态加锁"——Go 把前三者替你管了，你只管加锁。

## 2. Goroutine 后台任务 — 项目实例 `session/auto.go`

### 启动后台 goroutine (`main.go`)

```go
// serveCommand() 中，srv.Listen() 之前：
session.RunAuto(func(p string) ai.Summarizer {
    return application.SummarizerFor(p)
}, 30*time.Minute, otherProjects)
```

### 实现 (`session/auto.go`)

```go
func RunAuto(getSummarizer func(projectPath string) ai.Summarizer, interval time.Duration, projectPaths []string) {
    go func() {                    // ← goroutine 在这里启动
        time.Sleep(5 * time.Second) // 等数据库就绪
        safeRunAllProjects(home, projectPaths, getSummarizer)
        ticker := time.NewTicker(interval)
        defer ticker.Stop()
        for range ticker.C {       // ← 每 30 分钟触发一次
            safeRunAllProjects(home, projectPaths, getSummarizer)
        }
    }()
}
```

**逐行解释**：
1. `go func() { ... }()` — 启动一个 goroutine。这个匿名函数在**新 goroutine** 中执行，不会阻塞主函数
2. `time.Sleep(5 * time.Second)` — 暂停 5 秒等 DB 连接池初始化
3. `ticker := time.NewTicker(30 * time.Minute)` — 创建一个每 30 分钟触发一次的定时器
4. `defer ticker.Stop()` — 函数退出时停止 ticker，释放资源
5. `for range ticker.C { ... }` — 每次 ticker 触发时执行一次 `safeRunAllProjects`

**注意两点（当前版本的新变化）**：
- 第一个参数是**函数**（`getSummarizer func(projectPath string) ai.Summarizer`），不是 `ai.Summarizer`。因为现在 L2 摘要要用**每个项目自己的** AI 模型（读该项目 `.pmai/config.json`），所以每个 tick 都会对每个项目调一次 `getSummarizer`——配置改了不用重启就生效。这是 Go 里"依赖注入 + 惰性求值"的经典写法。
- `safeRunAllProjects` 内部用 `defer recover()` 兜底（`session/auto.go:37`）：单个项目 panic 不能杀掉整个 30 分钟循环。这也是 Go 的常见模式——**后台长任务必须自己 recover**。

### 和 Python 的对比

```python
# Python asyncio
async def run_auto(summarizer, interval):
    await asyncio.sleep(5)
    while True:
        await run_once(summarizer)
        await asyncio.sleep(interval)

asyncio.create_task(run_auto(summarizer, 1800))
```

Go 的 goroutine 更像轻量级 OS 线程——可以被 Go runtime 调度到多个 CPU 核上并行执行。Python 的 asyncio 是协程——所有协程跑在同一个线程里。而且 Go 没有 async/await 的"函数颜色"问题——**阻塞代码写起来就是阻塞的，不用涂颜色**：

```go
// Go: 阻塞的代码看起来就是阻塞的——不用涂颜色
go func() {
    data, _ := http.Get(url)     // 自动让出 CPU，不阻塞 OS 线程
    db.Exec("INSERT ...", data)  // 同上
}()
```

## 3. sync 包 — Mutex / RWMutex / Map

### `sync.Mutex` — 互斥锁 (`u/log.go`)

```go
var logMu sync.Mutex

func LogShared(tag string, format string, args ...any) {
    logMu.Lock()
    defer logMu.Unlock()
    // ... 写文件 ...  ← 同一时刻只有一个 goroutine 能执行这段
}
```

**为什么用 Mutex**：日志函数被 pipeline goroutine 和 proxy handler 并发调用。不加锁会导致文件写入交错、数据损坏。

**`defer logMu.Unlock()`** 保证 unlock 一定会执行——即使写文件 panic 也能 unlock。这是 Go 的惯用写法：lock 后立即 defer unlock。

### `sync.RWMutex` — 读写锁 (`proxy/context_inject.go`)

```go
var sessionCache struct {
    mu        sync.RWMutex   // ← 注意：是 RWMutex，不是 Mutex
    goals     []string
    updatedAt time.Time
}

func getCachedSessionGoals() []string {
    sessionCache.mu.RLock()          // ← 读锁 — 多个 goroutine 可同时持有
    if cacheValid() {
        defer sessionCache.mu.RUnlock()
        return sessionCache.goals
    }
    sessionCache.mu.RUnlock()        // ← 释放读锁

    sessionCache.mu.Lock()           // ← 写锁 — 独占
    defer sessionCache.mu.Unlock()
    // ... 查数据库并更新缓存 ...
}
```

**为什么要区分读写锁**：`goals` 被**频繁读取**（每次 LLM 请求都读一次）但**很少写入**（60s TTL 才刷新一次）。RWMutex 允许多个 goroutine 同时读——10 个并发的 LLM 请求不会互相阻塞。

这是 Go 中比 Mutex 更细腻的并发控制：如果你的数据结构**读多写少**，用 RWMutex 替代 Mutex 能大幅减少锁竞争。

### `sync.Map` — 并发安全 map (`proxy/context_inject.go`)

```go
var injectTracker sync.Map  // 不需要 make，零值即可用

func shouldInject(key string) bool {
    last, ok := injectTracker.Load(key)
    if !ok || time.Since(last.(time.Time)) > 5*time.Minute {
        injectTracker.Store(key, time.Now())
        return true
    }
    return false
}
```

**为什么不用普通 `map` + RWMutex**：普通 map 不是并发安全的——两个 goroutine 同时读/写会 crash。通常做法是 `map + sync.RWMutex`，但 `sync.Map` 在**读写分离、key 稳定**的场景下更简洁。不过要注意 `sync.Map` 的值是 `any` 类型，取值时需要 .(type) 类型断言。

**对 C++ 读者**：C++ 里没有任何并发安全的容器——`std::map` 并发读写就是 UB，你得自己加锁或上 `folly::ConcurrentHashMap`。Go 的 `sync.Map` 相当于语言内建了后者，前提是你接受它「值全是 `any`，要用类型断言取出来」这个代价。

## 4. Channel — 生产者 goroutine → 消费 channel

项目里最典型的 channel 用法是 SSE 流解析（`proxy/unified.go:161`）：

```go
func parseUpstreamSSE(r io.Reader) <-chan UnifiedStreamEvent {
    ch := make(chan UnifiedStreamEvent, 16)   // 带缓冲 channel
    go func() {
        defer close(ch)                        // 生产者结束 → 关闭 channel
        // ... 循环读取 SSE 事件 ...
        ch <- evt                              // 投递事件
    }()
    return ch   // 返回只读 channel <-chan
}
```

**要点**：
- `make(chan T, 16)` 创建**带缓冲** channel；`<-chan` 表示只读方向。
- 生产者 `go func(){...}()` 在后台填 channel，消费者 `for evt := range ch { ... }` 阻塞接收。
- **`close(ch)` 由生产者负责**——消费者用 `range` 循环，channel 关闭后自动退出。
- Go 的核心并发哲学：**"Don't communicate by sharing memory; share memory by communicating"**（不要通过共享内存通信，要通过通信共享内存）。

## 5. 为什么这么设计：并发的原理由来

### 6.1 goroutine 为什么这么轻？— GMP 模型

goroutine 不是 OS 线程。Go runtime 用 **GMP 模型**调度：

```
G = Goroutine（你的任务，~2KB 栈起步，按需增长）
M = Machine（OS 线程，真正的内核线程）
P = Processor（逻辑处理器，数量 = GOMAXPROCS，默认 = CPU 核数）

每个 P 挂一个本地 goroutine 队列；P 绑定一个 M；
goroutine 阻塞（如 I/O）时，P 换绑另一个 M 继续跑别的 goroutine。
```

- **栈可增长**：goroutine 从 2KB 开始，用多少涨多少。OS 线程栈固定几 MB，所以开一万个线程爆内存，开一万个 goroutine 才 ~20MB。
- **调度器是协作式抢占**：goroutine 在 channel 收发、I/O、`time.Sleep`、`runtime.Gosched()` 时主动让出；Go 1.14 起也支持异步抢占（防止死循环 goroutine 饿死别人）。
- **你不需要线程池**：`go f()` 本身就是"丢进池子"。C++ 里手写线程池、任务队列的活，Go runtime 替你做了。

### 6.2 channel 和 CSP 从哪来？

channel 的并发模型叫 **CSP**（Communicating Sequential Processes），来自 **Tony Hoare 1978 年的同名论文**。核心思想：

> **不要通过共享内存来通信，要通过通信来共享内存。**
> *Do not communicate by sharing memory; instead, share memory by communicating.*

锁（Mutex）的思路是"共享变量 + 加锁保护"；channel 的思路是"变量属于某个 goroutine，其他 goroutine 通过消息拿值"。channel 做两件事：
1. **传值**：`ch <- v` 把 v 交给接收方
2. **同步**：无缓冲 channel 的收发双方互相阻塞，天然是同步点

Go 的**设计原则**：并发原语要**简洁**——`go`、`chan`、`select` 三个关键词搞定。没有 actor、没有信号量、没有条件变量（都藏在标准库里）。

### 6.3 什么时候用 channel，什么时候用锁？

| 场景 | 用 |
|---|---|
| 一个 goroutine 产生数据，另一个消费 | **channel**（数据流） |
| 多个 goroutine 读同一个共享变量 | **RWMutex**（读多写少） |
| 多个 goroutine 写同一个文件/日志 | **Mutex** |
| 多个独立 goroutine 各自干活，不共享数据 | **都不需要**（各干各的） |
| 只初始化一次 | **sync.Once** |

经验法则：**有"生产/消费"关系用 channel；有"共享状态"用锁。** 项目里两种都有——`proxy/unified.go` 的 SSE 解析用 channel（生产→消费），`u/log.go` 的日志写入用 Mutex（共享文件）。

### 6.4 真实例子精读：SSE 流解析 (`proxy/unified.go:161`)

这是项目里最完整的 channel 用法，值得逐段读：

```go
func parseUpstreamSSE(r io.Reader) <-chan UnifiedStreamEvent {
    ch := make(chan UnifiedStreamEvent, 16)   // 带缓冲 16，防生产者阻塞消费者速度

    go func() {                                // 生产者 goroutine
        defer close(ch)                        // 无论怎么退出，都关闭 channel
        scanner := bufio.NewScanner(r)
        for scanner.Scan() {
            line := scanner.Text()
            if !strings.HasPrefix(line, "data: ") {
                continue                        // 跳过非 data 行
            }
            data := strings.TrimPrefix(line, "data: ")
            if data == "[DONE]" {
                ch <- UnifiedStreamEvent{Type: StreamDone, ...}
                continue
            }
            // ... json.Unmarshal 解析事件，ch <- evt ...
        }
    }()

    return ch        // 返回只读方向 <-chan，调用方只能收不能发
}
```

消费方（`proxy/emit_claude.go` 等）这样收：

```go
for evt := range ch {        // range 自动等 channel 关闭才退出
    switch evt.Type {
    case StreamDelta:  // ...
    case StreamDone:   // ...
    }
}
```

**为什么要用 channel 而不用回调**：SSE 事件是**异步到达**的流，channel 让"生产"和"消费"彻底解耦——生产者专注解析、消费者专注转发，两者靠 channel 对齐节奏。如果写成回调，层层嵌套难以阅读；写成 `range ch` 就是顺序代码。

### 6.5 关闭 channel 的规则

Go 对 close 有两条铁律：

1. **只有发送方（生产者）能 close**——接收方 close 会 panic。
2. **close 后再发会 panic**。所以生产者用 `defer close(ch)` 保证"无论中途怎么 return 都关掉"。

消费者用 `for v := range ch` 或 `v, ok := <-ch`（ok=false 表示已关闭）。**不要**用 `close` 当信号去通知别的 goroutine——那要用专门的 `done` channel。

### 6.6 用 `-race` 抓竞态

Go 内建数据竞争检测器：`go test -race ./...` 或 `go run -race`。它给编译产物注入检测代码，运行时发现两个 goroutine 无同步地读写同一变量就报警。

```bash
go test -race ./...   # 项目测试全带竞态检测
```

**对 C/C++ 读者**：这相当于 ThreadSanitizer（TSan）——但 `go test -race` 一行命令开箱即用，不用配 CMake、不用装 LLVM。

## 6. Go 的思考方式：并发

1. **并发 ≠ 并行**：并发是"程序结构"（同时处理多件事），并行是"执行"（同时跑多个核）。goroutine 给你并发；并行与否由 GOMAXPROCS 和调度器决定。
2. **"阻塞"不是坏事**：`ch <- v` 会阻塞等待接收方，这是**特性不是 bug**——它自动限速（背压），防止生产者淹没消费者。
3. **启动 goroutine 的瞬间就要想好它怎么退出**：`go f()` 前问一句"这个 goroutine 会泄漏吗？"后台任务必须自带 `defer recover()` 和退出条件（项目 `session/auto.go` 的 `safeRunAllProjects`）。
4. **能用 `select` 就不要手写多路等待**：
   ```go
   select {
   case <-done:      return
   case v := <-ch:   handle(v)
   case <-time.After(5 * time.Second):  // 超时
   }
   ```

## 7. 并发原语一览（都是真实用例）

| 原语 | 位置 | 干什么 |
|---|---|---|
| `sync.Mutex` | `u/log.go:16 logMu` | 保护日志文件写入 |
| `sync.RWMutex` | `proxy/context_inject.go:50 sessionCache.mu` | 读多写少的缓存（每次 LLM 请求读，60s 才刷新） |
| `sync.Map` | `proxy/context_inject.go:47 injectTracker` | 按 agent 记录注入状态（key 稳定、读写分离） |
| `sync.Once` | `api/server.go:18 sessionsInit` | 只启动一次会话 GC goroutine |
| `chan` + goroutine | `proxy/unified.go:161 parseUpstreamSSE` | 生产者 goroutine 把 SSE 事件喂给带缓冲 channel |

> 注意：项目**没有 worker pool**。并发模式是"一个长时后台任务一个 goroutine + channel 做流"。API 层的并发安全靠 `sync.Once` + `sync.RWMutex` 保护共享状态。
