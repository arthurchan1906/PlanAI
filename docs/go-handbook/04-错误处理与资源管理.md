# 04 · 错误处理与资源管理

> Go 没有 try/catch。本章讲透 error 返回、defer、recover、重试退避。
> 来源：原 `GO_GUIDE.md` 概念篇 §6 + 实战篇 §5/§8 + 高频语法。

## 1. 错误处理：返回错误而不是抛异常

Go 没有 `try/except`。所有可能失败的函数返回两个值：结果 + 错误。

```go
db, err := openDB()
if err != nil {
    return nil, err     // 向上传递
}
// 继续使用 db
```

**为什么**：Go 的设计哲学是"错误也是正常流程的一部分"。异常（Python 的 `raise`、JS 的 `throw`）会打断控制流，让代码跳跃。显式错误返回让每一步的失败处理都**可见**——没有隐藏的控制流跳转。

**C++ 对比**：现代 C++ 用 `std::expected<T, E>` / `tl::expected` 也是这个思路——错误是返回值，不是异常。Go 只是把它变成了语言内建。如果你写过 C++ 的 `if (auto err = doSomething(); err) { ... }`，Go 的 `if err != nil` 会非常亲切。

**代价**：代码里全是 `if err != nil`。习惯了就好。

## 2. 错误包装 — %w 保留错误链

```go
result, err := someFunction()
if err != nil {
    return nil, fmt.Errorf("step X failed: %w", err)  // %w 包装错误，保留原错误链
}
// 继续用 result
```

`%w` 让外层错误内层错误"链接"起来。上层可以用 `errors.Is(err, target)` / `errors.As(err, &target)` 判断错误链里是否包含特定错误——这是项目里 `retryOnBusy` 判断 `SQLITE_BUSY` 的依据。

## 3. 项目中怎么用 — 批处理循环里 `continue` 而非 `return`

```go
// session/run.go — 遍历 sessions 做批处理
rows, err := store.GetSessionMessagesFor(opts.ProjectPath, s.SessionID)
if err != nil {
    continue  // 这个 session 有异常，跳过它继续下一个
}
mergedRows := merged[s.Source+"|"+s.SessionID]
review := ReviewSession(opts.ProjectPath, s.SessionID, s.Source, CombineMessages(rows, mergedRows), len(mergedRows), nil)
```

**`continue` 而非 `return`**：这是一个批处理循环。单个 session 失败不应该阻止其他 session 的处理。Go 的错误处理让你可以在每一层精确决定"这个错误应该向上传递还是就地处理"。

## 4. nil-able interface — Go 特有的陷阱

```go
var summarizer ai.Summarizer = getClient()
if summarizer != nil {
    summarizer.Summarize(...)  // 可能 panic!
}
```

如果 `getClient()` 返回 `(*Client)(nil)`（即一个 nil 指针但类型是 `*Client`），`summarizer != nil` 会返回 **true**——因为 interface 值包含 (type, value) 两个部分，即使 value 是 nil，type 不为 nil 时 interface 就不是 nil。

**正确做法**：返回 interface 的方法应显式返回 nil：

```go
func newSummarizer() ai.Summarizer {
    if !enabled {
        return nil  // ← 直接返回 nil，不是 nil 指针
    }
    return &Client{...}
}
```

> 这是 Go 心智模型第一坑，详见 [08 · 常见坑](08-常见坑与心智模型.md)。

## 5. Defer — 资源清理的金标准

### 三个最常见用法

```go
// 1. 关闭文件
f, _ := os.Open("data.txt")
defer f.Close()

// 2. 释放锁
mu.Lock()
defer mu.Unlock()

// 3. 停止 ticker
ticker := time.NewTicker(30 * time.Minute)
defer ticker.Stop()
```

**执行顺序**：后进先出（LIFO）。如果注册了多个 defer，最后 defer 的最先执行。

**实际例子 (`session/auto.go`)**：

```go
go func() {
    time.Sleep(5 * time.Second)
    runOnce(summarizer)
    ticker := time.NewTicker(interval)
    defer ticker.Stop()          // goroutine 退出时停止 ticker
    for range ticker.C {
        runOnce(summarizer)
    }
}()
```

`defer` 在函数返回时执行，不是块结束时——注意 goroutine 内部也是一个函数作用域。

**对 C/C++ 读者**：`defer` 就是函数级 RAII 的替代品。C++ 里你用 `std::lock_guard`/`unique_ptr` 靠析构释放资源；Go 里用 `defer` 显式声明"函数退出时干什么"。区别是：C++ 的释放时机由对象生命周期决定，Go 的由 `defer` 注册顺序（LIFO）决定。

**Python 对比**：相当于 `with` / `finally`，但 `defer` 是**函数级**的（不只在一层 `with` 块内有效），而且即使 panic 也会执行。

### defer 的参数求值时机（经典坑）

```go
x := 1
defer fmt.Println(x)  // 参数 x 在 defer 这一行就求值 → 最终打印 1
x = 2                 // 改变不了上面

// 对比: 闭包捕获的是变量本身
x = 1
defer func() { fmt.Println(x) }()  // 最终打印 2 (执行时才取值)
x = 2
```

## 6. recover — 从 panic 中救回来

Go 没有异常，但有 `panic`（程序致命错误）。`recover` 可以拦下 panic，让 goroutine 不崩溃：

### 项目实例 1 — MCP 服务器 (`mcp/mcp.go:2679`)

```go
func (s *mcpServer) handleLine(line string) {
    var msgID interface{}
    defer func() {
        if r := recover(); r != nil {          // 任何 handler panic 都被兜住
            u.LogShared("MCP", "panic recovered: %v", r)
            s.sendError(msgID, -32603, "Internal error: "+fmt.Sprint(r))
        }
    }()
    // ... 正常处理 ...
}
```

**关键**：一个工具的 handler panic 不能杀掉整个 stdio 服务器——recover 后回一个 JSON-RPC error 继续服务。

### 项目实例 2 — 后台长任务 (`session/auto.go:37`)

```go
func safeRunAllProjects(home string, projectPaths []string, getSummarizer func(projectPath string) ai.Summarizer) {
    defer func() {
        if r := recover(); r != nil {
            u.LogShared("PIPELINE", "panic recovered: %v", r)
        }
    }()
    runAllProjects(home, projectPaths, getSummarizer)
}
```

单个项目 panic 不能杀掉整个 30 分钟循环。

> **对 C++ 读者**：`panic` ≈ C++ 异常 + `terminate` 的混合体，但**不要用来做业务控制流**。Go 的规则：panic = 程序 bug 或不可恢复状态；业务错误一律用 error 返回值。`recover` 只在"不能让整个服务死掉"的边界用（服务器入口、后台任务外层）。

## 7. 重试 + 指数退避 — SQLite 并发写冲突

多进程并发写 SQLite 会 `SQLITE_BUSY`。项目用两层重试：

```go
// session/auto.go:124 — 长流程重试，500ms / 1s / 2s 共 3 次
func retryPipelineBusy(fn func() error) error {
    var err error
    for i := 0; i < 3; i++ {
        err = fn()
        if err == nil {
            return nil
        }
        if !strings.Contains(err.Error(), "SQLITE_BUSY") && !strings.Contains(err.Error(), "database is locked") {
            return err        // 非 BUSY 错误，直接返回
        }
        time.Sleep(time.Duration(1<<uint(i)) * 500 * time.Millisecond)  // 1<<i: 1,2,4 → 500ms,1s,2s
    }
    return err
}
```

- `1<<uint(i)` 生成 1, 2, 4 —— 指数退避的位运算写法，很 Go。
- **只有 BUSY 错误才重试**，其他错误立即返回——重试要精确匹配错误类型，不能盲目重试。

> 类似地，`store/store.go:20` 有一个 `retryOnBusy` 用于单条写操作。这是项目处理 SQLite 并发冲突的统一模式。

## 8. 为什么这么设计：错误处理的原理由来

### 8.1 为什么 Go 没有异常？

Go 设计者**深入讨论过异常**（在语言提案阶段），最终否决。理由写进了 Go 的官方 FAQ：

1. **异常让错误路径不可见**：`try/catch` 把控制流跳来跳去，调用链上每一层都可能抛、可能吞。Go 想要的"每一行代码的错误都摆在明面上"做不到。
2. **异常鼓励"吞错误"**：`catch` 里写个 `log` 就继续，错误在传播过程中被静默丢弃。Go 的 `if err != nil` 逼你逐层面对。
3. **异常和接口、并发冲突**：goroutine 里抛的异常只能在本 goroutine 抓到，跨 goroutine 传播困难。error 作为返回值天然可传递。

> **对 C++ 读者**：C++ 的异常也有同样争议——很多 C++ 项目（Google 内部、嵌入式）明确禁用异常，用返回码。Go 只是把这个选择变成了语言默认。

### 8.2 error 本质是一个接口

```go
// 标准库定义——就这么短
type error interface {
    Error() string
}
```

任何有 `Error() string` 方法的类型都是 error。项目里 `ai/noop.go` 自定义错误就是这么干的：

```go
// ai/noop.go
type NoConfigError struct{}

func (e *NoConfigError) Error() string {
    return "AI not configured: set AI_ENDPOINT environment variable..."
}
```

**思维方式**：因为 error 是接口，所以你可以**用类型系统区分错误的种类**，而不是靠字符串匹配。

### 8.3 三种错误风格（按需选用）

| 风格 | 做法 | 适用 | 例子 |
|---|---|---|---|
| **哨兵错误** | 包级 `var ErrXxx = errors.New("...")`，调用方 `errors.Is(err, ErrXxx)` | 已知的错误种类 | `store` 包的空结果 |
| **自定义类型** | `type XxxError struct`，实现 `Error()`，`errors.As(err, &e)` | 需要取错误里的字段 | `ai.NoConfigError` |
| **包装** | `fmt.Errorf("...: %w", err)` | 层层传递，保留链路 | 项目里到处是 |

### 8.4 errors.Is / errors.As — Go 1.13 加入的解包利器

`fmt.Errorf("...: %w", err)` 把错误包起来后，如何判断"链路里有没有某个错误"？**不能** `==` 比较（外层不是同一个值），要用：

```go
// errors.Is：判断错误链里是否包含哨兵错误
if errors.Is(err, sql.ErrNoRows) {
    // 没查到数据，当作"空"处理
}

// errors.As：把错误链里某个类型的错误取出来
var nce *ai.NoConfigError
if errors.As(err, &nce) {
    // 是"AI 未配置"，走降级路径
}
```

项目里 `session/auto.go` 判断 SQLITE_BUSY 用的就是 `strings.Contains(err.Error(), "SQLITE_BUSY")`——这是**靠字符串匹配**的原始做法（因为现代码库没引入哨兵错误）。新代码应优先用 `errors.Is`。

### 8.5 "errors are values" — Rob Pike 的著名演讲

2015 年 Rob Pike 在 GopherCon 的演讲《Errors are values》核心观点：**错误处理不是样板代码，它是业务逻辑的一部分**。当 `if err != nil` 显得繁琐时，说明你的函数设计得不好——应该把错误处理做成数据流，而不是到处重复判断。

示例：项目里把"可能失败"封装成一个函数值，让错误处理集中：

```go
// session/auto.go — 把整段可能失败的逻辑塞进闭包，统一重试+记日志
err := retryPipelineBusy(func() error {
    r, rerr := Run(RunOpts{...})
    if rerr == nil {
        result = r
    }
    return rerr
})
```

**思维方式**：别急着写 20 个 `if err != nil`。停下来想：这段错误处理能不能**包装成一个可复用的函数**（重试、记日志、降级），让调用点只有一行？
