## 2. 三层 HTTP 路由器

```
web/server.go  ── 前端大门 ──► /pmai/* → api 处理器
                              /__proxy/* → proxy 处理器
                              / 其他 → 静态文件 + SPA 兜底
                                 │
api/server.go  ── API 路由 ──►  chain of handleXxxRoutes 每个返回 bool
                                 │
proxy/proxy.go ── 代理路由 ──►  http.NewServeMux + handler() 按路径 switch
                                 (/v1/messages, /v1/responses, /v1/chat/completions, /v1/models)
```

- **`web/server.go:41 Listen()`** 建一个 `http.NewServeMux`，用 `http.HandlerFunc` 包装后按前缀转发（静态/API/代理三岔口）。
- **`api/server.go:32 ServeHTTP`** 是"手工路由器"：一串 `handleXxxRoutes` 方法，每个内部 `switch path` 命中就处理并返回 `true`，否则返回 `false` 交给下一个。没有路由表、没有中间件库——纯 `net/http`。
- **`proxy/proxy.go:342 handler()`** 是代理的路径分发中心。

（代码细节见 [05 · 标准库实战](05-标准库实战.md) §2。）

## 3. 数据层：db ↔ store 分工

```
db/    只管"连上"：sql.Open("sqlite", 路径+WAL pragma)、建表/迁移、配置与凭据
store/ 只管"查询"：ListTasksFor / CreateTask / UpdateCommit ... 每个都是纯函数
                 （内部 pmdb.Open() → SQL → Scan 行 → 返回 []map[string]any）
```

- `modernc.org/sqlite` 是**纯 Go** 驱动，不需要 CGO——这是项目能在无 C 编译器的机器上构建的原因。
- 多进程并发写 SQLite 会 `SQLITE_BUSY`，项目用两层重试：`store/store.go:20 retryOnBusy`（单条写）和 `session/auto.go:124 retryPipelineBusy`（长流程，500ms/1s/2s 指数退避）。
- 有个次要数据库 `pmai_vectors.db`（`db/db.go:188 OpenVectors`）单独存 embedding 向量。

## 6. 从零学 Go 的实战路线（Python/C/C++ 视角）

> 你是先学的 Python（高层、动态）和 C/C++（底层、手动管理），Go 正好卡在中间。下面按**心智负担递增**排列，每一步都标了「你以前学过的什么能对上」。

### 阶段 0 — 热身：`u/u.go` + `u/log.go`（纯函数 + 一个 Mutex）

先看最没负担的：`u/u.go` 全是无状态工具函数。

```go
func NowISO() string { return time.Now().Format("2006-01-02T15:04:05") }
func Str(v any) string {                       // any = interface{} = Python 的 object
    if s, ok := v.(string); ok { return s }    // 类型断言 = Python 的 isinstance()
    return ""
}
```

- **对 Python**：`map[string]any` ≈ dict，`[]string` ≈ list，`func(...) (T, error)` ≈ 返回 `(result, error)` 元组。
- **对 C/C++**：Go 没有头文件、没有宏、没有运算符重载。`u/log.go` 里那个 `sync.Mutex` 就是你以前手动 `pthread_mutex_lock` 的东西——但这里一行 `defer logMu.Unlock()` 保证释放，**不会忘**。

### 阶段 1 — 接口即契约：`ai/interface.go` + `ai/noop.go` + `ai/http_client.go`

这是 Go 的灵魂，务必先看懂。对照代码见 [06 · 工程最佳实践](06-工程最佳实践.md) §2。

- **对 C++**：Go 的 interface ≈ 抽象基类，但**隐式满足**——不用写 `: public Summarizer`。只要你 `Client` 有 `Summarize(text, instruction string) (string, error)` 方法，它就是 `Summarizer`。这像 C++ 的 concept / duck typing 混血。
- **对 Python**：像 `Protocol` 但编译期检查。

### 阶段 2 — 程序入口与包：`main.go` + `app/app.go`

读 `main()`（`main.go:42`）→ 看 `switch os.Args[1]` 怎么把命令分发给 `init/setup/mcp/serve/proxy/chat/eval/agent/...`。再读 `app/app.go`——一个被全局共享的 `*App`（`var application = app.New()`），用 `sync.RWMutex` 保证并发读安全。

- **对 C**：`func main()` 就是 `int main()`，`os.Args[1]` 就是 `argv[1]`。Go 里 `os.Exit(serveCommand())` 就是你熟悉的 `return serve_command()`。

### 阶段 3 — 事件循环：`mcp/mcp.go Run()`

MCP 服务器是一个 **JSON-RPC over stdio 事件循环**：

```go
func (s *mcpServer) Run() error {
    for {
        line, err := s.reader.ReadString('\n')   // 阻塞读 stdin
        if err == io.EOF { return nil }
        s.handleLine(line)
    }
}
```

每个工具就是一个 `func(args map[string]interface{}) mcpToolResult`，注册就是 `s.addTool(MCPTool{...}, s.handleXxx)`。

- **对 Python**：这就是 `while True: line = stdin.readline()` 的服务器版，但**并发**更强（每个 `handleLine` 内部可以 `go` 出去）。
- **对 C/C++**：`map[string]MCPTool` + `map[string]mcpToolHandler` 就是一张**函数指针表**（C 里你可能用 `struct { const char *name; void (*fn)(...); }`）。

### 阶段 4 — 并发与定时：`session/auto.go`

后台管线：goroutine + `time.Ticker` + `defer recover()`。这是你第一次真正用到 Go 的并发。（代码细节见 [03 · 并发编程](03-并发编程.md) §2。）

- **对 C**：goroutine ≈ pthread，但 **2KB 栈起步**、随便开几千个、runtime 自动调度。没有 `pthread_create` 的参数结构体，没有 `pthread_join` 的等待负担。
- **对 Python**：不是 `threading`（受 GIL），不是 `asyncio`（单线程协程）。goroutine 是**真并行**，同时写代码像同步代码——**没有 async 函数颜色问题**。

### 阶段 5 — HTTP 与中间件：`proxy/proxy.go` + `web/server.go`

读 `proxy.go:342 handler(w, r)` 和 `web/server.go:61 wrapper`。

- **对 Python**：Go 的 `http.Handler` ≈ WSGI/ASGI 的 `app(environ, start_response)`，但内置。`http.NewServeMux` ≈ Flask 的路由表。
- **对 C++**：`responseWrapper` 嵌入 `http.ResponseWriter` 并重写 `WriteHeader`（`proxy/proxy.go:303`）≈ C++ 装饰器模式 / 继承后 override——但 Go 用**组合**而非继承。

### 阶段 6 — 数据库访问：`db/db.go` + `store/store.go`

（代码细节见 [05 · 标准库实战](05-标准库实战.md) §4。）

- **对 Python**：`database/sql` ≈ `sqlite3`，但行扫描是显式的：`row.Scan(&title)` 手动把列拷进变量——比 Python 啰嗦但类型安全。
- **对 C**：`?` 占位符 ≈ `?` 绑定参数（比 sprintf 拼 SQL 安全得多）。WAL 模式 + `busy_timeout(15000)` 是你以前调 SQLite 编译选项时见过的东西，这里一行 pragma 搞定。

### 阶段 7 — 大规模组织：`eval/pq_*.go`

最后看 eval 包：20 多个探测器，每个都是「Params 结构体 + `DetectXxx` 函数 + `FormatXxxHuman` 渲染器」的**统一形状**。这是 Go 组织大型代码库的方式——**不用继承/不用注册表，靠文件名约定和一致的函数签名**。`eval/pq_process.go:28 BuildProcessReport` 是它们的编排者。

## 7. 读代码的思维方式：跟着数据流走

读 Go 代码（尤其是这种大项目）不是从头读到尾，而是**沿着一条数据流**：

```
Hook 捕获（hook/）→ 存库（store/discussion.go）→ 分析（analyze/ 或 eval/）
     → 展示（api/ → web/ 或 mcp/ → 你的 AI agent）
```

举例——你想搞清楚"一条 agent 会话是怎么被记录、分析、展示的"：

1. **入口**：`hook/hook_claude.go:22 ProcessClaudeHook()` — 从 stdin 读 JSON
2. **落库**：调 `store.LogDiscussion(...)` 写进 SQLite
3. **分析**：`session/run.go` 的 `Run()` 批量读会话 → `ReviewSession()` 出 `ReviewResult`
4. **展示**：`api/query.go` 的 `handleQueryRoutes` 里 `case "discussions":` 拉数据给前端
5. **Agent 侧**：`mcp/mcp.go` 的 `handleSearch` 把同一条数据变成工具返回

**练习**：读任何功能，都先回答三问——**数据从哪来？在哪存？给谁看？** 三问定位后，代码自然展开。
