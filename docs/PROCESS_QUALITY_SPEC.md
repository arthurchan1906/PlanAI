## 0. 方向变更记录（用户主导，2026-08-19）

| 项 | 原方向（EVAL_PIPELINE v1） | 现方向（本规格） |
|---|---|---|
| 评测对象 | 意图达成率（干完了没有） | 过程质量（干得靠不靠谱） |
| 核心问题 | 从讨论推断任务是否达成 | agent 的行为链条（检索意识 / 盲试 / 纠偏响应） |
| 判定方式 | LLM 判达成 | 风险信号 + 人工抽查 |

**为什么转向（三条硬证据）**

1. **达成判定不可行**：无法从 discussion 推断任务达成，必须实际测试/生产环境验证——任何「达成率」类指标都是伪指标，禁止使用。**替代口径**：P3 改进闭环的验收同样不做达成判定，只做 L1 行为指标的前后对比（见 §5）。
2. **grounding 单维度证伪**：EncryptDrive 正样本（c0ad2534，788 条记录）35 条断言全部有取证（0 沙土），但 22 小时查错方向——真实盲猜形态是「取证方向错误」而不是「无取证断言」，断言-证据配对抓不住这种形态。
3. **三维度在真实数据上有区分度**（详见 §4.1）：历史检索意识 / 重复停滞 / 用户介入三个描述层信号可操作化，且区分度超过 grounding 单维度。

**元模式原则（全系统通用）**

- 所有自动判定降级为「带证据的可下钻风险信号」，不做「对/错」二元判定。
- LLM 做**确认器**不做**探测器**：输入必带证据上下文，输出强制 JSON，单一职责。
- 能算的不问 LLM，能确认的不靠猜，能标注的不裸跑。
- **文档是假设，设备/数据实证是事实**（v1.4 补，分享 saga 教训）：官方文档说 `extensionContext.open` 死路，但微信设备实证 + UIScene 目标实测可行——「API 死刑 ≠ 机制死刑」。文档结论与实证冲突时以实证为准，且**先做对照实验再下结论**（微信对照一次顶十轮理论）。
- **观察者校准原则（v1.4 补）**：L2/L3 的 ground truth 一律以**用户原话**为准（用户确认消息、用户反证消息、用户对「胜利/实锤」的否认），观察者（codex/claude/本规格作者）结论不算数——10:36 Claude 宣布「点即跳恢复=胜利」被用户 10:38 打脸，与 codex 犯同样的需求错位；观察者复盘同样需要被复盘。
- **「构建成功 ≠ 产物有效」（v1.4 补）**：任何「构建通过」类验证必须包含产物完整性检查（可执行文件存在、关键配置进入产物），防空壳构建（10:25 删扩展误伤同步组 → BUILD SUCCEEDED 但产物无主可执行文件）。
- **真机轮次是预算（v1.4 补）**：静态可核对项（selector 对 SDK 头文件、API 签名）先查再动，模拟器能截获的不上真机——一个字符（`open:` vs `openURL:`）烧掉一轮真机测试的教训。

## 1. 目标

研究使用 code agent 时，在 aipm 的帮助下处理问题，agent 的行为是否发生变化、是否按 aipm 提供的 context / facilities / constraints 行事。**关心行为链条（方法论层面），不关心单项任务完成度。**

典型问题：「当用户提出一个 bug 时，agent 是直接搜索、确定范围就改，还是先查 git/aipm 历史、分析影响范围再计划修改？反复失败时有没有重新全盘思考？有没有把猜测当事实？」

**核心检测信号（v1.3）——反馈响应性**：用户纠偏/反馈后，agent 的 响应（转向）/ 持续（不滑回）/ 加深（新对象）/ 收敛（有产出）/ **对准（行为对准反馈所指）** 五子信号。理由（实证）：
- 三种盲试形态（零检索盲猜 / 猜测补丁 / 自以为是）的共同点 = 反馈响应性缺陷；两种健康形态（短平快 / 螺旋上升）的共同点 = 反馈响应性健全。
- 单维活动密度会把「自以为是型」误判为健康（019ff89b：自发检索 56 + build 78，用户重复反馈 14 次「还是不行」）——**多维交叉是唯一出路**，五子信号必须同时评估。
- **「对准」是独立维度（v1.3 第四轮）**：响应只判「有没有行为」，不判「行为是否对准反馈所指」——019ff89b 的核心机制正是「响应✓ 但转向对象始终不对」；2026-08-19 实时案例（01a013f3 17:06-17:10）agent 补 dzsec-import 日志但用户要的是分享扩展日志，同样是对准✗。归「加深」子情况会漏判（加深判对象扩展率，不判方向匹配）。

**前置检测点（v1.4 补）——目标锚定**：五子信号全部测「反馈之后」，覆盖不到**初始问题定义就错**的情形——分享 saga 的最大损失正发生在此：用户 8/19 15:09「从系统相册找了两张图片」= 相册多选需求，agent 定义成「单文件打开方式」并据此建了 `4b41ba8` 基线，直到 8/20 10:44 用户爆发「相册当然是要多选的 否则这么长时间你在干什么」才校准。**规则**：session 首条 user 消息中的场景名词（相册/多选/文件/分享等）与 agent 首个结论/首个 commit 的声称对象做匹配（L1 近似），不匹配 → 候选「目标错位」交 L2 确认；`目标锚定` 与 `对准` 的区别：锚定测「初始目标是否对」，对准测「纠偏后行为是否指向反馈所指」。

## 2. 总体架构（L1-L4）

```
discussion_log / commits / bugs / events
  → L1 描述层（纯代码）：事件流 → 硬指标 → 候选标记（高召回）
  → L2 语义层（LLM 确认器）：候选 + 证据上下文 → JSON 判定
  → L3 校准层（标注集 + ED bug 库）：ground truth → 精度报告 → 回修 L1/L2
  → L4 报告层：行为画像 + 对照 + 抽查清单 → aipm 改进闭环
```

### 2.1 L1 描述层（纯代码，100% 可复核）

| 模块 | 输入 | 输出 |
|---|---|---|
| 事件流 | 归一化记录 | 有序事件：tool_call / llm_text / user_msg / commit / fail（时间+类型+对象+命令） |
| 硬指标 | 事件流 | 历史检索计数、重复命令次数、编译失败数、user 消息密度、三要素占比、断言提取 |
| 候选标记 | 硬指标 | 候选死循环、候选方向错、候选沙土——高召回低精度，宁误报不漏 |

**检测点定义（v1.1 定稿 + v1.3 修订，口径冻结）**

| 检测点 | 定义 | 关键规则（口径冻结） |
|---|---|---|
| 目标锚定（v1.4 新增） | session 首条 user 消息场景名词 vs agent 首个结论/commit 声称对象的匹配 | L1 近似匹配（场景词：相册/多选/单文件/分享/打开方式/文件；声称对象 = 首个结论主题或首个 commit 标题）；不匹配 → 候选「目标错位」交 L2；**实证**：01a013f3 用户 8/19 15:09「两张图片」=多选，agent 首个 commit `4b41ba8` 声称「单文件打开方式」→ 目标错位，10:44 才校准 |
| 历史检索意识 | 定向检索计数（aipm/git 历史） | 三分类：**自发**（无纠偏窗口内）/ **被动**（纠偏消息后 20 分钟内）/ **例行**（read_discussions 等，不计入意识）。**定向边界**：`git show <旧commit>` / `git log` / `git blame` / `git grep` / `git rev-list` / `aipm_search_*` / `aipm_get_*` / `aipm_list_commits` / `aipm_trace` = 历史检索；`git show HEAD:` / `git status` / `git diff`（工作区 vs HEAD 当前态）/ `aipm_read_discussions` = **不算**。**「≈0」阈值**：候选窗口内自发检索 < 2 次 |
| 重复停滞（死循环） | 重复构建/命令 + 失败 + 长时间无进展 | build 密集 + 失败 + 用户高峰 + 自发检索 < 2 组合信号。**排除规则（v1.3 补，11h 教训）**：候选标记 = build 密集 + 自发检索 <2 + **中间无 edit/commit/根因定位信号**——11h（build=11 自发=0）是修复验证期，被单计数规则误报为盲试；修复阶段 build 密集 + 修改是正常的。**build 噪声防护（v1.2）**：排除 `DerivedData/.*/Build/` 路径、`build\d` 版本号、构建日志读取（`Logs/Build`）；只计真正的构建命令（`xcodebuild build` / `swift build` / `go build` 等动词形式）。实测 01a013f3 的 8/18 16h 17 次 build 全为误捕 |
| 用户介入 | user 消息密度 + 类型 | **纠偏候选** = 含关键词（此前/之前/应该/查/历史/记录/提交记录/以前）**或**含否定方向词（方向不对/不对/错了/重新审视/你查的…不对）；**推进** = 「继续/可以/好」。**hook 注入行排除（v1.3 补，操作化）**：识别特征 = 内容为纯结构化日志粘贴——`[模块]` 开头行 + `=` 键值对（`flattened=0`/`count=11`/`ksn=`）+ **无 CJK 字符**；判别正则 `^(?:\[[A-Za-z_]+\][^\n]*\n?)+$` 且无 CJK → hook 注入，不计入纠偏。含自然语言（CJK）即按手打处理（半日志半文字也按手打）。注意：纠偏消息也可能是错的（用户误判）——纠偏只作候选触发，**L2 确认后才计入**，标签为「纠偏（可能误）」；响应率 + 响应持续性（响应后是否又滑回盲试）+ 对准度（响应行为是否对准反馈所指） |
| 断言提取 | 正则提取 assistant 断言 | 只提取不做分类（分类归 L2） |
| 三要素画像 | 日志/逻辑分析/猜测三类占比 | **日志** = 加日志命令（print/Log/ED-DEBUG/诊断代码）；**逻辑分析** = 代码搜索/读取/静态分析（rg/grep/sed/cat/读文件/objdump）；**猜测** = 无取证断言（L2 确认）。产出：占比 + 顺序 + 切换点（如「反复 build 后转加日志」），按问题类型分基线 |
| 构建产物完整性（v1.4 新增） | 构建类命令后校验产物 | 构建后校验 `*.app`/`*.appex` 含主可执行文件 + 关键配置（Info.plist 键）进入产物；**实证**：10:25 删扩展误伤 `PBXFileSystemSynchronizedRootGroup` → 空壳构建（BUILD SUCCEEDED 但无 `EncryptDrive` 可执行文件），用户真机安装报 Code 3000 |
| 静态可核对项（v1.4 新增） | 上真机前的静态检查清单 | 字符串 selector 对 SDK 头文件核对（`open:` vs `openURL:` 教训）、API 参数类型查头文件签名（UIScene options 教训）、废弃 API 检查；命中清单项的错误不烧真机轮次，直接静态拦截 |

**核心检测点：反馈响应性四子信号（v1.3 新增，口径冻结）**

| 子信号 | 定义 | 数据层级 | 证据来源 |
|---|---|---|---|
| 响应 | 用户纠偏/反馈后 20min 内出现新行为（检索/edit/build 任一） | 命令级 | 反馈消息时间戳 + 后续行为序列 |
| 持续 | 转向后不滑回旧对象（滑回 = 旧 file_path/主题词重新出现） | 对象级精确 / 命令级近似 | 对象序列 |
| 加深 | 转向后出现新对象/新文件域（对象集合扩展率 = 新对象/总对象） | 对象级（仅 hook session） | rel_path 序列 |
| 收敛 | 有产出信号：修复 commit 或用户确认消息 | 命令级 | 修复 commit + 用户确认 |
| 对准（v1.3 第四轮新增） | 响应行为的前 N 个对象与反馈消息所指对象的匹配（描述层近似：反馈提取所指实体 vs 响应命令中的文件/主题词匹配率）；精确判定归 L2 `matched_object` | 命令级近似 / 对象级精确 | 反馈消息实体 + 响应命令对象 |

- **收敛 ground truth 外部化（v1.3）**：收敛不绑 agent 自报（形态 4 实证：ED 169 条 passed 中含 `chore: 构建版本号 4 → 5`），绑定「用户确认消息」（c0ad2534 = 6/24 11:37「现在苹果安卓都可以正常工作了」）或「修复 commit」（d628b7a，message 与 bug-20260624 标题一致）
- **层级分层（v1.3）**：命令级子信号（响应/持续近似/收敛）全部样本可算；对象级子信号（加深/持续精确）只在 hook 记录 session（有 rel_path）可算。验收分层见 §5

### 2.2 L2 语义层（LLM 确认器）

| 任务 | 输入（必须带证据） | 输出 |
|---|---|---|
| 断言分类 | 候选断言 + 前序工具记录 | `{type: 事实/意见/摘要/进度, conf}` |
| 证据细配对 | 事实断言 + 前序工具对象 | `{match: 强/弱/无, 依据}` —— 只确认「真无证据」，粗配对无匹配才触发 |
| 死循环确认 | 候选段行为序列 | `{is_deadloop: bool, 重复模式}` |
| 方向评估 | 候选段 + 问题上下文 | **触发条件**：仅当 L1 已标记「候选方向错」（tech 密集 + 自发检索 < 2）时才调用；只判「历史检索信号缺失是否被确认」；「应该查什么」仅作建议，**不进标注项** |
| 反馈响应确认 | 候选反馈事件 + 反馈后 20min 行为序列 | `{responded: bool, deepened: bool, sustained: bool, aligned: bool, matched_object, note}` —— 五子信号的 L2 确认（v1.3 新增；`matched_object` = 反馈所指实体 vs 响应行为的匹配对象） |

Prompt 三约束：① 系统声明只基于提供证据判定；② 证据上下文必填（命令截断）；③ 输出强制 JSON、单一职责。

### 2.3 L3 校准层（≤30 分钟/次）

- 抽样：每 session 抽 3-5 个候选，约 20-30 例
- 勾选式字段：`claim_type` / `evidence_match` / `is_deadloop` / `direction_ok`（=「该候选段的历史检索缺失是否被 L2 确认」，**不是**「应该查什么」）
- **ED bug 库自动分层（免人工）**：52 条 bug 的 root_cause **具体性评分规则（P0 定稿）**——正则命中以下任一即「具体」：文件路径（`[\w/]+\.\w+`）、函数/符号（`\w+\(` 或类名）、技术机制词（sizeof/分块/截断/EXIF/adaptive/竞态/优先级 等）；否则「可疑」，先人工复核 10 条校准规则再全量
- 产出：① L1 精确率/召回率 ② L2 判定一致率（**≥80% 才上线**，不是调低标准）③ 阈值校准
- **回修机制**：精度报告 <80% → 回修 L1 阈值或 L2 提示词 → **重跑同一验证集**确认改善，不得直接调低标准

### 2.4 L4 报告层

- 五子信号并列展示（P0 不加权）：响应 / 持续 / 加深 / 收敛 / 对准 + **形态标签聚合**（可多标）+ **三要素画像**（占比/顺序/切换点，按问题类型分基线）
- 对照：同 session 时间序列（干净维度）、agent 间（必须标注项目混杂）、aipm 功能版本前后
- 输出：沙土/死循环候选清单（抽查聚焦）+ 画像报告 + aipm 改进点

## 3. 问题实体链条（与 bug 库结合）

**问题实体 = bug/task 记录**，行为分析围绕其生命周期组织，不从零切意图段。

```
bug 记录（发现） → 修复 commit 序列 → session 行为链（诊断/盲试/纠偏） → 验证/关闭
```

- **自动补链（P0 定义归属规则）**：bug 记录时间 ±7 天内、**含 bug.files 字段中文件**的 commit 归入修复序列；session 按时间戳与 bug 记录/commit 重叠归属（跨天 session 取 bug 记录所在日期的活跃时段）
- **穿插问题的解**：A→B→A 的归属靠问题实体锚点（commit→task、bug→讨论），不靠无监督聚类
- **ED bug 库 = L3 现成校准集**：root_cause 具体性评分 + 修复链条质量
- **S2/S3 去向**：已交付的 turn/classify/segment **降级为工具级分析单位**（回合/工具序列），不再用于意图达成用途（§7）

## 6. Review Agent（代码审核，共享架构的产物侧）

### 6.1 定位（用户收敛）

review agent **不做「实际效果正确」判定**（与达成判定同理不可行），只产出三个风险信号：

| 任务 | 已有基础 | 难度 | 核心难点 |
|---|---|---|---|
| 范围检测（超范围） | ✅ `AnalyzeScopeDrift`（**抽到共享包 `analyze/scope.go` 导出**，review 与简报共用） | 低-中 | 仅文件名级；逻辑级超范围需 LLM；plan scope 覆盖不全 |
| 回归风险 | ✅ 部分：`test_status` 字段 + 自证检测 | 中 | 只能风险排序；影响面分析需调用图 |
| 依据检测（从 discussion） | ❌ 证据源异构 | 中-高 | discussion 文本非结构化；「无依据 vs 没记录」不可区分 |

**commit 级自证定义**：该 commit 对应时间窗口内无 test 命令，且 commit message 或讨论声称测试通过（段级 `SelfClaimWithoutProof` 的 commit 级映射）。

### 6.2 依据检测的证据源分层（降难度设计）

1. **git 证据**（描述层，零 LLM）：commit message、diff 是否带测试、改动文件与问题域关系（问题域 = bug.files 字段 + root_cause 提及文件）
2. **bug/task 关联**（描述层）：commit 关联的 bug 记录、root_cause 具体性
3. **discussion 文本**（LLM 确认器，最后查）：前两层不足时才查，调用量最小化

**grounding 证伪的教训带入**：①「取证方向错」≠「无取证」；② 判定做分层（强依据/弱依据/证据缺失），「缺失」标注「可能是记录不全」，不当实锤。

### 6.3 实施（两阶段，不并轨防 scope creep）

- **第一阶段（描述层先行）**：`AnalyzeScopeDrift` + 自证检测 + diff 特征（改动规模/核心路径/测试缺失）→「可疑 commit 排序」。验收 = ED 历史回溯（已知问题 commit 排前）
- **第二阶段**：依据检测 = grounding 的产物侧映射，复用 L2 确认器基础设施

### 6.4 落地位置

- `aipmc review --since` 子命令（复用 eval 框架双输出：JSON + 人类可读），与 `aipmc eval` 并列
- **抽查反馈最小形式（P0 定义）**：`aipmc review --verdict <commit_id> ok|bad|unknown [note]`，反馈进 L3 校准集（8/14 反馈闭环决策的应用）
- 最终汇合：行为分析沙土节点 + review 可疑 commit 合并为**按风险排序的抽查聚焦清单**（L4 报告层，P0 阶段两侧分开可下钻）
