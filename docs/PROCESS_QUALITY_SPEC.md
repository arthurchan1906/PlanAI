## 0. 方向变更记录（用户主导，2026-08-19）

| 项 | 原方向（EVAL_PIPELINE v1） | 现方向（本规格） |
|---|---|---|
| 评测对象 | 意图达成率（干完了没有） | 过程质量（干得靠不靠谱） |
| 核心问题 | 从讨论推断任务是否达成 | agent 的行为链条（检索意识 / 盲试 / 纠偏响应） |
| 判定方式 | LLM 判达成 | 风险信号 + 人工抽查 |

**为什么转向（三条硬证据）**

1. **达成判定不可行**：无法从 discussion 推断任务达成，必须实际测试/生产环境验证——任何「达成率」类指标都是伪指标，禁止使用。**替代口径**：P3 改进闭环的验收同样不做达成判定，只做 L1 行为指标的前后对比（见 §5）。
2. **grounding 单维度证伪**：EncryptDrive 正样本（c0ad2534，788 条记录）35 条断言全部有取证（0 沙土），但 22 小时查错方向——真实盲猜形态是「取证方向错误」而不是「无取证断言」，断言-证据配对抓不住这种形态。
3. **三维度在真实数据上有区分度**（详见 §4.1）：历史检索意识 / 重复停滞 / 用户介入三个描述层信号可操作化，且区分度超过 grounding 单维度。

**元模式原则（全系统通用）**

- 所有自动判定降级为「带证据的可下钻风险信号」，不做「对/错」二元判定。
- LLM 做**确认器**不做**探测器**：输入必带证据上下文，输出强制 JSON，单一职责。
- 能算的不问 LLM，能确认的不靠猜，能标注的不裸跑。
- **文档是假设，设备/数据实证是事实**（v1.4 补，分享 saga 教训）：官方文档说 `extensionContext.open` 死路，但微信设备实证 + UIScene 目标实测可行——「API 死刑 ≠ 机制死刑」。文档结论与实证冲突时以实证为准，且**先做对照实验再下结论**（微信对照一次顶十轮理论）。
- **观察者校准原则（v1.4 补，第二轮限定消除自指矛盾）**：L2/L3 的 **ground truth 判定**（agent 是否达成 / 是否实锤 / 是否收敛）一律以**用户原话**为准（用户确认消息、用户反证消息、用户对「胜利/实锤」的否认），观察者（codex/claude）结论只作候选与证据、**不进入 ground truth 判定**——10:36 Claude 宣布「点即跳恢复=胜利」被用户 10:38 打脸，与 codex 犯同样的需求错位；观察者复盘同样需被复盘。**此限定只约束判定层**：观察者的描述性记录（行为序列/时间戳/工具调用）仍可作为证据输入；本规格自身的结论同样是假设、不作 ground truth，须经用户原话或客观行为序列校准。
- **「构建成功 ≠ 产物有效」（v1.4 补）**：任何「构建通过」类验证必须包含产物完整性检查（可执行文件存在、关键配置进入产物），防空壳构建（10:25 删扩展误伤同步组 → BUILD SUCCEEDED 但产物无主可执行文件）。
- **真机轮次是预算（v1.4 补）**：静态可核对项（selector 对 SDK 头文件、API 签名）先查再动，模拟器能截获的不上真机——一个字符（`open:` vs `openURL:`）烧掉一轮真机测试的教训。
- **设计者校准原则（v1.4 第三轮补，第四轮补用户原话逐条引用）**：本框架的设计者（codex/claude）的讨论过程同样受本框架检测——**规格演化史本身就是 ED agent 行为的镜像**，实证：codex 读到「先看 diff 再写」却直接提交（采纳度✗）；codex 用 019ff89b shell 检索论证「工具采用」（取证方向错，与「断言-证据方向错」同构）；Claude「去重是 cache 命中率下降元凶」实锤被 A/B 实验证伪（实锤被反证，与「平台限制实锤」同构）；codex 19h/0.18-6.85 数字自报未验证（与「空壳构建 BUILD SUCCEEDED」同构）。**用户原话是最高优先级 ground truth——逐条引用为校准信号**：「联系整个项目」（需求错位：初期审核聚焦功能点/规格细节，目标定义窄了）、「结合真实使用数据」（验证责任：task 锚定假设未先查数据就推出）、「审核过于简短」（测试成本：review 深度不足）、「你似乎开窍了但还差点东西」（框架没量自己：检测点已建但未用于自身）、「你们也是 agent」（自我检测通道缺失：设计者与 ED agent 同构）。落地机制见开放问题 O1·设计者实例。

## 1. 目标

研究使用 code agent 时，在 aipm 的帮助下处理问题，agent 的行为是否发生变化、是否按 aipm 提供的 context / facilities / constraints 行事。**关心行为链条（方法论层面），不关心单项任务完成度。**

典型问题：「当用户提出一个 bug 时，agent 是直接搜索、确定范围就改，还是先查 git/aipm 历史、分析影响范围再计划修改？反复失败时有没有重新全盘思考？有没有把猜测当事实？」

**核心检测信号（v1.3）——反馈响应性**：用户纠偏/反馈后，agent 的 响应（转向）/ 持续（不滑回）/ 加深（新对象）/ 收敛（有产出）/ **对准（行为对准反馈所指）** 五子信号。理由（实证）：
- 三种盲试形态（零检索盲猜 / 猜测补丁 / 自以为是）的共同点 = 反馈响应性缺陷；两种健康形态（短平快 / 螺旋上升）的共同点 = 反馈响应性健全。
- 单维活动密度会把「自以为是型」误判为健康（019ff89b：自发检索 56 + build 78，用户重复反馈 14 次「还是不行」）——**多维交叉是唯一出路**，五子信号必须同时评估。
- **「对准」是独立维度（v1.3 第四轮）**：响应只判「有没有行为」，不判「行为是否对准反馈所指」——019ff89b 的核心机制正是「响应✓ 但转向对象始终不对」；2026-08-19 实时案例（01a013f3 17:06-17:10）agent 补 dzsec-import 日志但用户要的是分享扩展日志，同样是对准✗。归「加深」子情况会漏判（加深判对象扩展率，不判方向匹配）。

**前置检测点（v1.4 补）——目标锚定**：五子信号全部测「反馈之后」，覆盖不到**初始问题定义就错**的情形——分享 saga 的最大损失正发生在此：用户 8/19 15:09「从系统相册找了两张图片」= 相册多选需求，agent 定义成「单文件打开方式」并据此建了 `4b41ba8` 基线，直到 8/20 10:44 用户爆发「相册当然是要多选的 否则这么长时间你在干什么」才校准。**规则**：session 首条 user 消息中的场景名词（相册/多选/文件/分享等）与 agent 首个结论/首个 commit 的声称对象做匹配（L1 近似），不匹配 → 候选「目标错位」交 L2 确认；`目标锚定` 与 `对准` 的区别：锚定测「初始目标是否对」，对准测「纠偏后行为是否指向反馈所指」。

## 2. 总体架构（L1-L4）

```
discussion_log / commits / bugs / events
  → L1 描述层（纯代码）：事件流 → 硬指标 → 候选标记（高召回）
  → L2 语义层（LLM 确认器）：候选 + 证据上下文 → JSON 判定
  → L3 校准层（标注集 + ED bug 库）：ground truth → 精度报告 → 回修 L1/L2
  → L4 报告层：行为画像 + 对照 + 抽查清单 → aipm 改进闭环
```

### 2.1 L1 描述层（纯代码，100% 可复核）

| 模块 | 输入 | 输出 |
|---|---|---|
| 事件流 | 归一化记录 | 有序事件：tool_call / llm_text / user_msg / commit / fail（时间+类型+对象+命令） |
| 硬指标 | 事件流 | 历史检索计数、重复命令次数、编译失败数、user 消息密度、三要素占比、断言提取 |
| 候选标记 | 硬指标 | 候选死循环、候选方向错、候选沙土——高召回低精度，宁误报不漏 |

**检测点定义（v1.1 定稿 + v1.3 修订，口径冻结）**

| 检测点 | 定义 | 关键规则（口径冻结） |
|---|---|---|
| 目标锚定（v1.4 新增，第二轮修正） | session 首条 user 消息场景名词 vs agent 首个结论/commit 声称对象的匹配 | L1 近似匹配（**场景词只取用户侧词汇**：相册/多选/图片/分享/文件；**不含 agent 定义词**如「单文件」「打开方式」——场景词是锚定基准，必须来自用户原话；声称对象 = 首个结论主题或首个 commit 标题）；不匹配 → 候选「目标错位」交 L2；**实证**：01a013f3 用户 8/19 15:09「两张图片」=多选，agent 首个 commit `4b41ba8` 声称「单文件打开方式」→ 目标错位，10:44 才校准 |
| 历史检索意识 | 定向检索计数（aipm/git 历史） | 三分类：**自发**（无纠偏窗口内）/ **被动**（纠偏消息后 20 分钟内）/ **例行**（read_discussions 等，不计入意识）。**定向边界（v1.4 执行方案配套补全）**：`git show <旧commit>` / `git log` / `git blame` / `git grep` / `git rev-list` / `aipm_search_*`（search_context/smart_search/search_discussions）/ `aipm_trace` = **历史检索**；`aipm_get_*`（get_task/get_plan/get_commit 详情）+ `aipm_list_commits` = **状态读取（当前态），不计入历史检索意识**；`git show HEAD:` / `git status` / `git diff`（工作区 vs HEAD 当前态）/ `aipm_read_discussions` = **不算**。**「≈0」阈值**：候选窗口内自发检索 < 2 次 |

### 2.2 L2 语义层（LLM 确认器）

### 2.3 L3 校准层（≤30 分钟/次）

- 抽样：每 session 抽 3-5 个候选，约 20-30 例
- 勾选式字段：`claim_type` / `evidence_match` / `is_deadloop` / `direction_ok`（=「该候选段的历史检索缺失是否被 L2 确认」，**不是**「应该查什么」）
- **ED bug 库自动分层（免人工）**：52 条 bug 的 root_cause **具体性评分规则（P0 定稿）**——正则命中以下任一即「具体」：文件路径（`[\w/]+\.\w+`）、函数/符号（`\w+\(` 或类名）、技术机制词（sizeof/分块/截断/EXIF/adaptive/竞态/优先级 等）；否则「可疑」，先人工复核 10 条校准规则再全量
- 产出：① L1 精确率/召回率 ② L2 判定一致率（**≥80% 才上线**，不是调低标准）③ 阈值校准
- **回修机制**：精度报告 <80% → 回修 L1 阈值或 L2 提示词 → **重跑同一验证集**确认改善，不得直接调低标准

### 2.4 L4 报告层

- 五子信号并列展示（P0 不加权）：响应 / 持续 / 加深 / 收敛 / 对准 + **形态标签聚合**（可多标）+ **三要素画像**（占比/顺序/切换点，按问题类型分基线）+ **信号偏好矩阵**（信号源 × 响应质量，按信号源分层输出——防止统一检测点把信号源差异平均掉）

## 3. 问题实体链条（与 bug 库结合）

**问题实体 = bug/task 记录**，行为分析围绕其生命周期组织，不从零切意图段。

```
bug 记录（发现） → 修复 commit 序列 → session 行为链（诊断/盲试/纠偏） → 验证/关闭
```

- **自动补链（P0 定义归属规则）**：bug 记录时间 ±7 天内、**含 bug.files 字段中文件**的 commit 归入修复序列；session 按时间戳与 bug 记录/commit 重叠归属（跨天 session 取 bug 记录所在日期的活跃时段）
- **穿插问题的解**：A→B→A 的归属靠问题实体锚点（commit→task、bug→讨论），不靠无监督聚类
- **ED bug 库 = L3 现成校准集**：root_cause 具体性评分 + 修复链条质量
- **S2/S3 去向**：已交付的 turn/classify/segment **降级为工具级分析单位**（回合/工具序列），不再用于意图达成用途（§7）

## 6. Review Agent（代码审核，共享架构的产物侧）

### 6.1 定位（用户收敛）

review agent **不做「实际效果正确」判定**（与达成判定同理不可行），只产出三个风险信号：

| 任务 | 已有基础 | 难度 | 核心难点 |
|---|---|---|---|
| 范围检测（超范围） | ✅ `AnalyzeScopeDrift`（**抽到共享包 `analyze/scope.go` 导出**，review 与简报共用） | 低-中 | 仅文件名级；逻辑级超范围需 LLM；plan scope 覆盖不全 |
| 回归风险 | ✅ 部分：`test_status` 字段 + 自证检测 | 中 | 只能风险排序；影响面分析需调用图 |
| 依据检测（从 discussion） | ❌ 证据源异构 | 中-高 | discussion 文本非结构化；「无依据 vs 没记录」不可区分 |

**commit 级自证定义**：该 commit 对应时间窗口内无 test 命令，且 commit message 或讨论声称测试通过（段级 `SelfClaimWithoutProof` 的 commit 级映射）。

### 6.2 依据检测的证据源分层（降难度设计）

1. **git 证据**（描述层，零 LLM）：commit message、diff 是否带测试、改动文件与问题域关系（问题域 = bug.files 字段 + root_cause 提及文件）
2. **bug/task 关联**（描述层）：commit 关联的 bug 记录、root_cause 具体性
3. **discussion 文本**（LLM 确认器，最后查）：前两层不足时才查，调用量最小化

**grounding 证伪的教训带入**：①「取证方向错」≠「无取证」；② 判定做分层（强依据/弱依据/证据缺失），「缺失」标注「可能是记录不全」，不当实锤。

### 6.3 实施（两阶段，不并轨防 scope creep）

- **第一阶段（描述层先行）**：`AnalyzeScopeDrift` + 自证检测 + diff 特征（改动规模/核心路径/测试缺失）→「可疑 commit 排序」。验收 = ED 历史回溯（已知问题 commit 排前）
- **第二阶段**：依据检测 = grounding 的产物侧映射，复用 L2 确认器基础设施

### 6.4 落地位置

- `aipmc review --since` 子命令（复用 eval 框架双输出：JSON + 人类可读），与 `aipmc eval` 并列
- **抽查反馈最小形式（P0 定义）**：`aipmc review --verdict <commit_id> ok|bad|unknown [note]`，反馈进 L3 校准集（8/14 反馈闭环决策的应用）
- 最终汇合：行为分析沙土节点 + review 可疑 commit 合并为**按风险排序的抽查聚焦清单**（L4 报告层，P0 阶段两侧分开可下钻）

## 9. 置顶锚与执行协议（v1.4 第五轮新增，用户 14:41/14:43 提醒「执行会打折、需要置顶规格纠偏」）

> 定位：规格是静态文档，agent 执行时「读一次 → 执行 → 偏离累积（简化/拍脑袋/验证不充分）→ 规格不在上下文 → 不可纠偏」。本节的 **L0 锚**让规格在执行全程成为始终可见的锚，执行偏差时拉回——**这是「锚定执行」（事前+事中持续可见），不是「检测执行退化」（事后监控）**。

### 9.1 L0 锚（执行全程可见，不可偏离；最小集）

执行 agent 的上下文里始终有：
1. **元模式三原则**（§0 提炼）：风险信号非判定（不下对/错二元结论）/ 验证责任在提出者（能算的不问 LLM、能确认的不靠猜）/ 用户原话为最高优先级 ground truth
2. **核心检测点七清单**（只列名字，细节在 L1 按需读）：**用户介入（用户原话）** / 目标锚定 / 信号-行为响应 / 主动触发 / 历史检索意识 / 重复停滞（死循环） / 构建产物完整性——沿革：五清单漏「重复停滞」（第六轮补，与 P0a 验收①一致）→ 六清单漏「用户介入」（第七轮补，ED saga 最大教训：偏离 = 偏离用户原话）
3. **验收标准**（P0a 三条）：死循环时段分离（召回 ≥80%、误报 ≤15min）/ 自发被动比方向性（ED 内 ≥5 倍）/ 目标锚定 + 空壳构建单样本检出

**清单选择依据（v1.4 第六轮补，第七轮修正）**：① P0a 验收①-③ 直接覆盖——目标锚定/历史检索意识/重复停滞/构建产物完整性（正样本来源）；② 核心检测信号族——信号-行为响应/主动触发（§2.1 v1.4 新增）+ 历史检索意识（§1 v1.3）；③ **用户介入（用户原话）为最高优先级项**——ED saga 实证：需求错位（15:09）/纠偏被解释（17:06）/测试成本（10:16）全部是「偏离用户原话」，用户介入是**偏离风险最高、也最能拉回**的锚（第六轮「低偏离风险」判断错误，第七轮认账修正）。**不在锚中的理由**：静态可核对属 P0a2 实现（非验收①-③ 直接覆盖）。

### 9.2 执行 checkpoint（每个实现单元四步对照，**客观输出物可外部验证**——不是「我检查了」，是可验证产物；ED 五条准则的工程化，见 `decision-20260820-133258`）

| checkpoint | 对照锚 | 偏离信号 → 纠正 |
|---|---|---|
| 实现前 | 目标锚定：我要实现的是规格要的检测点吗？ | **客观输出物**：「L0 锚 ↔ 当前实现」映射表（每个检测点/每条验收 ↔ 实现位置） |
| 实现中 | 验证责任：实现验证了吗？ | **客观输出物**：验证证据（真实数据运行结果，不是「能编译」） |
| 实现后 | 采纳度：读的规格条款执行了吗？ | **客观输出物**：「规格条款 ↔ 实现」勾选表（逐条勾选，漏项 = 未达标） |
| 汇报时 | 数字自报：数字验证了吗？ | **客观输出物**：与规格口径的核对结果（不一致 = 重算后附证据） |

**checkpoint 粒度（v1.4 第六轮补）**：每个检测点（实现单元）执行四步对照；阶段（P0a1/P0a2）完成时输出**汇总映射表**（阶段 × 检测点 × 对照物位置）。

**对照物必查（v1.4 第七轮补，第八轮补验收执行者）**：用户不审阅（现实），对照物不能只是「备查」——执行报告（含对照物）作为**规格验收的输入**，P0a1 完成时比对验收①-③；对照物是必查项，不是可选的抽查材料（否则「客观对照物」退化为「自评的另一形态」——生成但不被验证）。**验收执行者（第八轮补）**：P0a1 完成后执行者提交验收报告（含对照物），**用户抽查对照物 + 验收①-③ 的数据结果**——对照物是用户抽查的抓手，不是替代用户。

### 9.3 纠偏回路（锚定执行为主、外部反馈为补充——第六轮修正）

- **主通道 = 锚定执行**：agent 每个 checkpoint 输出客观对照物（§9.2），偏离时对照 L0 锚回读修正——**结构化自检，不是主观自评**：对照物是映射表/证据/勾选表，可被外部抽查验证，绕开 O1 的自评主观性困境
- **补充信号 = 外部反馈**（用户/其他 agent/review 指出偏差）：用户现实「项目 100% 由 code agent 完成、程序员不审阅」——外部反馈频率极低，**不能作为主通道**（第五轮「外部反馈为主」与用户现实矛盾，本轮修正）；但外部反馈出现时是**强信号**（用户原话 = 最高优先级 ground truth，直接回读锚修正）；规格执行期间的 review 节点是外部反馈的固定触发点

### 9.4 注入形态与 Goodhart 边界

- L0 锚进 `InjectSessionContext`（像 goals 一样每次请求注入），agent 执行规格时锚始终在上下文
- **Goodhart 边界（与 §8 风险表对齐）**：注入的是**行为准则**（你要按这些原则执行、向用户原话锚定）——**不是检测点细节**（L1 阈值/规则不注入，防 agent 适应检测点）；检测点细节仍按 §8「不注入 agent 可见上下文」
- **注入模板（v1.4 第六轮补，第七轮补依赖处理）**：固定三段文本——① 元模式三原则（§0 原文）② 用户原话锚定提示（「用户原话 = 最高优先级 ground truth，当前任务的用户原话 = …」——**依赖处理（第七轮补）**：P0a1 阶段用 bug/task 记录中的用户原话（若有）或任务描述暂代；P3「需求场景字段」是结构化最终来源，模板字段预留）③ 当前阶段验收标准（P0a 三条）

### 9.5 与 O3 的关系

- §9 = 执行侧的**主动锚**（agent 每步自查，降低偏离发生）；O3 = 分析侧的**被动检测**（L2 评估准则落实率，度量偏离残余）——互补，§9 不替代 O3。

### 9.6 讨论收敛判据（v1.4 第七轮补，元层——用框架测我们自己的讨论）

- **收敛判据**：一轮 challenge 中**实质设计问题**（影响架构/检测点语义/验收标准）< 1 个、只剩定义/措辞类 → 冻结规格评审，进入执行
- **执行期修正输入**：规格修订以**执行反馈**（P0a1 数据结果）为准，不再讨论驱动——数据反馈闭环（decision-20260814 准绳）用在我们自己身上
- **防表演型收敛**：不得为「显得收敛」而把实质问题降级为措辞问题（O3 防表演原则的延伸）；第七轮 C1/C2 为实质 → 未达收敛，修完即进冻结评审
- **判定主体（第八轮补）**：「实质 vs 措辞」的最终判定以**用户冻结评审**为准（观察者校准原则：用户是最高 ground truth）；codex/claude 的收敛宣告只是建议，不替代用户裁定
